# 大厂高频面试题精讲 (05-02-pydantic-v2-core-validation)

---

### Q1: 既然项目已经写了严格的 Type Hints，为什么在 Web 接口入口处依然必须引入类似 Pydantic 的运行时校验？

#### 🎯 面试官考点
- 编译期类型系统（Compile-time Static Analysis）与外部非受信运行期边界（Untrusted Runtime Boundary）。

#### 💡 满分回答模板
1. **静态检查的“真空地带”**：
   - TypeScript、Python Type Hints 等静态类型系统**仅在本地开发与 CI 构建期间有效**；代码一旦上线运行，Python 虚拟机执行字节码时对类型注解毫无感知；
   - 外部客户端通过 HTTP 发送的 JSON 请求体本质上是**完全不受信的纯字符串/原始字典**。调用方可以随意传入负数、超长文本、缺少必须字段甚至传入 SQL 注入载荷；
2. **Pydantic 的工业级护城河**：
   - **运行时类型强行清洗与转换（Type Coercion）**：能安全地将符合格式的字符串自动转换为标准整数或 `datetime` 对象；
   - **业务规则边界校验（Validation）**：限制长度、正则匹配、数值范围、联动逻辑，确保进入核心业务层的数据 100% 纯净合规。

### Q2: Pydantic V2 相比 V1 做了哪些颠覆性重构？pydantic-core 在架构层面是如何解决性能瓶颈的？

#### 🎯 面试官考点
- 现代微服务底层性能优化、Rust 语言在 Python 基础设施中的工程落地。

#### 💡 满分回答模板
1. **V1 的性能瓶颈根因**：
   - Pydantic V1 的校验逻辑完全用 Python 编写。在处理大规模深层嵌套字典时，需要创建海量的临时 Python 局部变量与函数调用栈，受限于解释器执行效率与垃圾回收开销，在高吞吐 API 下往往成为系统最大的 CPU 热点。
2. **V2 的架构重组（Rust 引擎 `pydantic-core`）**：
   - **核心完全下沉至 Rust**：整个数据校验、类型转换与错误收集流水线全部使用 Rust 编写并直接编译为 C-ABI 动态链接库；
   - **性能飞跃 5~17 倍**：单次请求的解析直接在底层原生紧凑内存中完成遍历，彻底杜绝了频繁申请小对象的开销；
   - **严格模式与宽松模式分离**：引入 `strict=True` 模式，禁止跨类型自动转换（例如严格禁止把字符串 `"123"` 转换为数字 `123`），满足金融级系统的确定性要求。

### Q3: 在 Pydantic V2 中，@field_validator 与 @model_validator 的触发时机有何不同？如何实现跨字段联动校验？

#### 🎯 面试官考点
- 校验生命周期阶段划分、局部字段验证与全局模型验证的协作。

#### 💡 满分回答模板
1. **触发时机与职责对比**：
   - **`@field_validator`（单字段校验器）**：
     - 在**单个字段完成基本类型解析后立即针对该字段触发**；
     - 此时只能看到当前字段的值，无法可靠访问其他尚未完成解析的兄弟字段；
   - **`@model_validator`（模型级联动校验器）**：
     - 包含两种模式：`mode="before"`（在所有字段解析前的原始字典阶段触发）与 **`mode="after"`（在所有字段均独立解析通过后触发）**；
     - 在 `mode="after"` 下，入参已经是完整初始化的模型实例 `self`，所有字段均已具备强类型。
2. **跨字段联动校验最佳实践**：
   - 跨字段逻辑（如“结束时间必须晚于开始时间”、“两次密码输入一致”）**必须使用 `@model_validator(mode="after")`**，确保比对的双方字段均已合法解析，逻辑清晰且无空指针风险。
