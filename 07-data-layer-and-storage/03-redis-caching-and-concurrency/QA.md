### Q1: 请详述“缓存穿透”、“缓存击穿”与“缓存雪崩”的本质区别及其在大厂生产架构中的标准防御方案。

#### 🎯 面试官考点
- 高并发分布式存储防灾设计、大厂核心考题必背标准八股。

#### 💡 满分回答模板
| 灾难类型 | 发生根因场景 | 核心危害 | 大厂生产标准防御解决方案 |
| :--- | :--- | :--- | :--- |
| **缓存穿透**<br>(Cache Penetration) | 客户端恶意请求**数据库和缓存都不存在的非法 Key**（如黑客扫描负数 ID） | 请求每次都直接穿透打到数据库，DB 算力耗尽崩溃 | 1. **空值缓存（Cache Null）**：即使 DB 为空也向 Redis 缓存短 TTL 哨兵值；<br>2. **布隆过滤器（Bloom Filter）**：在接入层直接拦截判定不存在的 Key。 |
| **缓存击穿**<br>(Cache Breakdown) | **单一热点超高并发 Key**（如爆款秒杀商品）在某瞬间**缓存刚好过期失效** | 瞬间数万并发同时发现缓存缺失，全量涌向 DB 重复计算回源 | 1. **互斥锁机制（SET NX）**：只允许抢到锁的一个请求回源查库重建缓存，其余请求等待重试；<br>2. **逻辑永不过期**：后台异步任务探测定期主动刷新。 |
| **缓存雪崩**<br>(Cache Avalanche) | **海量不同 Key 被设置了完全相同的固定过期时间**（如整点集体失效），或 Redis 节点故障宕机 | 大面积缓存同时消失，整个持久层瞬间被海量洪峰压垮雪崩 | 1. **TTL 随机抖动（Jitter）**：固定基础时长 + 随机秒数（如 300~600 秒随机范围）；<br>2. **Redis 高可用集群架构**：配置主从哨兵或 Cluster 集群。 |

### Q2: 如何使用 Redis 实现一个高可用的分布式锁（Distributed Lock）？为什么单纯写 setnx 会有死锁隐患？

#### 🎯 面试官考点
- 分布式并发控制、原子性保障（Atomicity）、防误删锁与锁续期。

#### 💡 满分回答模板
1. **传统分步 `setnx` 的致命死锁缺陷**：
   - 过去写法：先调用 `setnx lock_key 1`，紧接着调用 `expire lock_key 30`；
   - **致命 Bug**：如果执行完 `setnx` 后，当前服务容器刚好崩溃宕机或被网络重启，`expire` 命令未被执行，该锁在 Redis 中将**永久存在且永不超时，造成全系统死锁**！
2. **现代标准实现（原子合并命令）**：
   - 必须使用 Redis 2.6.12+ 的原子组合指令：
     ```python
     # NX: 键不存在时才设置; EX: 自动附加过期时间，一条命令原子完成
     acquired = await redis.set("lock:order:100", request_uuid, nx=True, ex=10)
     ```
3. **安全释放锁（防误删）**：
   - 必须将当前请求的唯一 ID（如 UUID）作为 value 存入；
   - 释放锁时，**必须使用 Lua 脚本先比对 value 是否与自身 UUID 一致，确认是自己持有的锁才能执行 del**，防止业务执行超时导致把别人的锁误删除。

### Q3: 为什么在高并发异步 Python 中必须使用 Redis 连接池（ConnectionPool）复用连接？

#### 🎯 面试官考点
- TCP 三次握手与四次挥手系统开销、TIME_WAIT 状态与连接复用机制。

#### 💡 满分回答模板
1. **非连接池模式的系统级毁灭代价**：
   - 若每次执行命令都新建连接，每秒 5,000 次请求将触发 5,000 次完整的 **TCP 三次握手 + 密码认证 + 四次挥手**；
   - 这不仅增加毫秒级网络延迟，还会导致操作系统的本地端口被瞬间耗尽，产生海量 **`TIME_WAIT`** 状态套接字，直接打爆系统内核网络栈；
2. **连接池（ConnectionPool）的运行收益**：
   - 预先创建并长久维持一组已通过鉴权的活动 TCP 长连接；
   - 协程执行命令时直接从池中借出一个连接，命令执行完非阻塞归还；全生命周期无任何握手握手开销，充分发挥 Redis 10 万+ QPS 的极致吞吐。
