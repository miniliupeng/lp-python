### Q1: SQLAlchemy 2.0 相比 1.x 版本做了哪些重大架构重构？为什么说 2.0 语法是现代异步 Python 后端的绝对标准？

#### 🎯 面试官考点
- ORM 演进历史、统一 2.0 编程风格、强类型系统（PEP 484）与异步底层架构。

#### 💡 满分回答模板
1. **彻底废除 1.x 隐式查询 API（Legacy Query API）**：
   - 1.x 的 `session.query(User).filter(...)` 包含大量隐式魔法与动态属性探测；
   - 2.0 全面统一为显式的 **`select(User).where(...)`** 顶层函数，语法结构与原生 SQL 高度对齐，可读性与可维护性极大提升。
2. **全面拥抱 Python 静态类型提示（`Mapped[T]`）**：
   - 2.0 引入了基于类型注解的 **`Mapped[int] = mapped_column()`** 声明方式；
   - 静态类型检查器（MyPy, Pyright）能够精准推导出 `user.id` 的真实类型，在编译期拦截非法属性赋值。
3. **原生异步引擎（`AsyncEngine` 与 `AsyncSession`）**：
   - 将 greenlet 上下文与异步驱动（如 `asyncpg`, `aiosqlite`）深度整合，彻底消除了旧版依赖同步驱动阻塞事件循环的重大隐患。

### Q2: 为什么生产环境中必须精细化配置数据库连接池（Pool Size, Max Overflow, Pool Recycle）？连接泄漏通常是由什么编码习惯导致的？

#### 🎯 面试官考点
- 数据库连接池底层参数优化、连接生命周期管理与防 OOM/句柄泄露生产经验。

#### 💡 满分回答模板
1. **三大核心参数配置调优依据**：
   - **`pool_size`（常驻连接数）**：通常根据应用日常平均并发量设置为 10~20；连接常驻内存避免频繁进行 TCP 三次握手与身份验证开销；
   - **`max_overflow`（突发允许扩展数）**：当遇到流量尖峰突增时，允许临时创建的最大连接缓冲池（如 10~20 个），用完后立即销毁；
   - **`pool_recycle`（连接强行回收周期）**：MySQL 等数据库默认会在 8 小时断开空闲连接；若未设置 `pool_recycle`（建议设为 1800 秒），应用在夜间空闲后发起第一个请求会因为使用已被远端关闭的僵尸连接而抛错。
2. **连接泄漏（Connection Leak）的致命坏习惯**：
   - **未将 Session 纳入上下文管理**：手动写 `session = Session()`，但在后续业务处理或远程调用抛出未捕获异常时跳过了 `session.close()`；
   - **长生命周期异步操作持有数据库连接**：在获取了数据库连接后，中途去执行了一个耗时数十秒的大模型请求或慢外部 HTTP 接口，导致珍贵的数据库连接被无谓霸占闲置，拖垮整站连接池。

### Q3: 请详述 AsyncSession 的生命周期管控。为什么业界强烈推崇“单请求单会话（Session per Request）”原则？

#### 🎯 面试官考点
- 工作单元模式（Unit of Work Pattern）、跨请求并发状态污染隔离。

#### 💡 满分回答模板
1. **工作单元（Unit of Work）模式**：
   - `AsyncSession` 不仅仅是连接句柄，它在内存中维护了一级缓存（Identity Map）与当前事务跟踪的实体状态机；
2. **推崇 Session per Request 的核心理由**：
   - **状态隔离保障**：如果多个并发 HTTP 请求共用一个全局 Session，当请求 A 发生回滚（Rollback）时，会把请求 B 正在编辑的未提交数据一并清空甚至提交脏数据；
   - **零死锁与优雅生命周期**：配合 FastAPI 等现代 Web 框架的依赖注入（`Depends`），在请求到达时自动创建 Session，请求正常返回时自动 `commit`，任何报错时自动 `rollback`，并在最后无条件 `close` 归还连接，实现 100% 确定性的连接安全回收。
