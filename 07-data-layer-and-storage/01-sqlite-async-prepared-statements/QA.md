# 大厂高频面试题精讲 (06-01-sqlite-async-prepared-statements)

---

### Q1: 什么是 SQL 注入漏洞？预编译语句（Prepared Statements）在数据库内核层面是如何彻底杜绝注入的？

#### 🎯 面试官考点
- 编译原理前端、SQL 语法树（AST）生成阶段与字符字面量绑定的内核机制。

#### 💡 满分回答模板
1. **SQL 注入的底层原理**：
   - 注入的本质是：**数据与代码的边界被模糊**；
   - 当使用字符串拼接 SQL 时（如 `f"SELECT * FROM users WHERE name = '{user_input}'"
2. **预编译语句（Prepared Statements）的免疫机制**：
   - **两阶段分离处理**：
     1. **准备阶段（Prepare）**：数据库先对带有占位符（如 `?` 或 `$1`）的静态 SQL 模板进行编译，确定好抽象语法树结构（AST）与固定的执行计划；
     2. **执行阶段（Execute）**：应用层将用户输入的参数单独打包发送给数据库引擎；
   - 数据库引擎在这一阶段**绝不重新解析语法树**，仅仅将传入的数据作为叶子节点直接赋值给对应的变量内存槽位。因此不论输入什么符号，都只能作为普通文本比较，从数学上 100% 杜绝了 SQL 注入。

### Q2: 为什么在异步 Python 服务中绝对不能直接使用标准库的同步 sqlite3 模块？aiosqlite 的底层原理是什么？

#### 🎯 面试官考点
- 阻塞 I/O 对事件循环的破坏、底线程池代理封装异步化的工程落地。

#### 💡 满分回答模板
1. **禁止使用标准库 `sqlite3` 的致命原因**：
   - 标准库 `sqlite3` 是由底层 C 语言编写的同步 C 扩展，在进行磁盘读写、文件锁争用时会发生**不可中断的操作系统系统调用阻塞**；
   - 在高并发异步服务中，这会直接锁死主线程的事件循环，使所有并发用户的 HTTP 请求被物理挂起。
2. **`aiosqlite` 的底层工作原理**：
   - SQLite 本身是一个嵌入式 C 库，原生并不暴露异步 Socket 句柄（无法使用 epoll）；
   - `aiosqlite` 的设计核心是：**在后台启动一个专用的独立工作线程（Worker Thread）**，所有 SQL 操作通过内部队列派发给后台线程同步执行；
   - 主线程事件循环仅需 `await` 线程执行完毕通知的 Future 对象，从而巧妙地把同步磁盘阻塞调用包装成了不阻塞事件循环的异步接口。

### Q3: 什么是 SQLite 的 WAL（Write-Ahead Logging）模式？相比传统回滚日志模式它在高并发读写上有何决定性优势？

#### 🎯 面试官考点
- 存储引擎并发模型、读写锁争用优化与故障恢复日志。

#### 💡 满分回答模板
1. **传统回滚日志（Rollback Journal）的痛点**：
   - 在写事务期间，数据库必须在磁盘创建回滚日志并持有全库排他锁（Exclusive Lock）；
   - 在写入提交完成之前，**全库的所有读取操作全部被阻塞等待**（写阻塞读，读也阻塞写），并发吞吐量极低。
2. **WAL 模式的并发优势（读写并发互不阻塞）**：
   - **写操作不直接改写主数据库文件**：所有的写事务被顺序追加写入独立的 `-wal` 预写日志文件中，开销极小且速度极快；
   - **读操作无需等待写完成**：读取事务直接结合主数据库文件与 WAL 内存索引，读取历史快照视图（MVCC 隔离）；
   - **核心优势**：实现了真正的 **“读不阻塞写，写不阻塞读”**，并发吞吐量提升数倍，在大厂边缘容器与微服务本地缓存中是必开选项。
