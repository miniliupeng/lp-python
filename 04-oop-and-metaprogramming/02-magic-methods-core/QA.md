### Q1: 简述 __str__ 与 __repr__ 的核心设计意图差异。生产日志打印为什么应优先依赖 __repr__？

#### 🎯 面试官考点
- Python 核心设计哲学、文本契约规范与生产调试排障可用性。

#### 💡 满分回答模板
1. **设计受众与核心意图差异**：
   - **`__repr__()`（面向开发者与机器调试）**：目标是**精确、无歧义**。理想状态下其输出应该能够被复制进解释器直接执行（即 `eval(repr(obj)) == obj`）；
   - **`__str__()`（面向普通用户展现）**：目标是**友好、易读**，隐藏复杂的内部实现细节（如格式化日期字符串）。
2. **回退机制与生产日志原则**：
   - **自动回退规则**：当一个类只实现了 `__repr__` 时，调用 `str(obj)` 或 `print(obj)` 会自动回退调用 `__repr__`；但反过来若只实现了 `__str__`，调试查看容器列表时依然只会显示原始内存地址；
   - **生产日志铁律**：在关键链路日志输出中，始终使用 `logger.info("Token: %r", token)`（或 f-string `{token!r}`），保留类型引号与结构全貌，彻底避免空字符串、空白符或浮点舍入导致的伪无感知 Bug。

### Q2: 为什么在 Python 中重写了 __eq__ 之后，默认的 __hash__ 会被自动置为 None？两者必须协同一致的底层数学依据是什么？

#### 🎯 面试官考点
- 哈希表（Hash Table）底层查找算法、碰撞解决与哈希不变量（Hash Invariant）。

#### 💡 满分回答模板
1. **哈希表查找的两阶段机制**：
   - 当在字典中查找 `dict[key]` 时，底层分两步：
     1. 首先计算 `hash(key)` 找到对应的哈希表桶（Bucket）；
     2. 若桶中有数据，再通过 `key == stored_key`（调用 `__eq__`）比对是否真正相等。
2. **破坏哈希不变量的严重灾难**：
   - **不变量法则**：若 `a == b`，则 `hash(a)` 必须等于 `hash(b)`；
   - 默认情况下，类继承自 `object` 的 `__hash__` 是基于**对象在内存中的物理地址指针**计算的；
   - 如果开发者重写了 `__eq__`（改为按照业务属性判断相等），但未重写 `__hash__`，就会出现：**两个逻辑上相等的对象，哈希值却完全不同**！
   - 导致该对象被存入哈希表后，外部即便构造了一个内容完全一样的对象去读取，也会因为哈希值不同去查找了不同的桶槽，**永远无法查出该数据**！
3. **解释器的防御性置空**：
   - 因此 Python 规定：只要用户类重写了 `__eq__`，解释器无条件将 `__hash__` 覆写为 `None`（标记为不可哈希）。强迫开发者必须显式实现具有不可变保障的 `__hash__`。

### Q3: 什么是可调用对象（Callable Object）？在哪些生产架构中利用 __call__ 比纯函数更有优势？

#### 🎯 面试官考点
- Python 可调用协议（Callable Protocol）、有状态函数与面向对象结合的高级抽象。

#### 💡 满分回答模板
1. **本质与协议要求**：
   - 在 Python 中，任何实现了 **`__call__()`** 魔术方法的类实例，都可以像普通函数一样使用小括号 `instance(*args, **kwargs)` 直接执行；
   - 使用内置函数 `callable(instance)` 将返回 `True`。
2. **生产架构中相比纯函数的决定性优势（状态性与解耦）**：
   - **复杂的有状态执行器（Stateful Callables）**：
     纯函数若想保持状态必须依赖闭包或全局变量，不利于序列化、动态重置与继承扩展；
     通过类实现 `__call__`，可以在 `__init__` 中注入昂贵的外部资源（如数据库客户端连接池、模型权重矩阵），而在 `__call__` 中纯粹执行推断调用；
   - **中间件与拦截器架构**：在 WSGI/ASGI 框架或 LangChain 链式管道中，组件普遍设计为可调用对象，兼备高度内聚的面向对象配置能力与函数式流水线组装的灵活性。
