# 大厂高频面试题精讲 (03-05-oop-inheritance-and-mro)

---

### Q1: 什么是 Python 中的方法解析顺序（MRO）？C3 线性化算法解决了什么核心痛点？

#### 🎯 面试官考点
- 多继承拓扑决议、图深度优先遍历（DFS）的缺陷与 C3 线性化（C3 Linearization）数学准则。

#### 💡 满分回答模板
1. **MRO 的核心定义**：
   - MRO（Method Resolution Order）是 Python 在面向对象多继承体系中，用于决定属性和方法查找搜索优先级的**唯一线性类序列**；
   - 存储在每个类对象的 `__mro__` 元组属性中。
2. **传统 DFS 遍历的历史缺陷（Python 2.2 之前）**：
   - 早期 Python 使用深度优先从左到右搜索；
   - 在菱形继承（`D(B, C)`，`B(A)`，`C(A)`）中，若类 C 覆写了 A 的方法，旧版 DFS 会沿着 `D -> B -> A` 提前命中基类 A 中未被更新的方法，导致子类 C 的覆写被静默无视！
3. **C3 线性化算法的三大黄金准则**：
   - **局部优先级（Local Precedence Order）**：优先保证在子类括号中写在左侧的父类排在右侧父类之前；
   - **单调性（Monotonicity）**：如果在父类的 MRO 列表中类 X 在类 Y 之前，那么在任何衍生子类的 MRO 中，X 必须依然排在 Y 之前；
   - 算法通过拓扑排序与合并（Merge）操作，彻底根除了菱形继承中的属性覆写失效问题。

### Q2: 为什么在多继承架构中必须使用 super() 而严禁使用 BaseClass.__init__(self) 直接硬编码调用？

#### 🎯 面试官考点
- `super()` 的动态绑定与协同多任务（Cooperative Multiple Inheritance）机制。

#### 💡 满分回答模板
1. **传统硬编码调用的致命硬伤**：
   - 如果类 B 显式调用 `BaseA.__init__(self)`，类 C 也显式调用 `BaseA.__init__(self)`；
   - 当汇聚子类 D 同时继承 B 和 C 时，**基类 `BaseA` 的构造方法必然会被重复执行两次**；
   - 并且类 B 的硬编码调用彻底断绝了将调用控制权移交给其“兄弟类 C”的可能性。
2. **`super()` 的真正底层本质**：
   - **`super()` 绝对不代表“调用直接父类”！**
   - 它的真实行为是：**以当前运行时的调用实例（`self`）的全量 `__mro__` 序列为全局依据，精准查找当前所在类在 MRO 列表中的“下一个紧邻类”**；
   - 在 D 的继承链中，类 B 中的 `super()` 查找到的下一个类正是类 C。它像接力棒一样协同流转，保证多继承树上的每一个类被**精确且仅被执行一次**。

### Q3: 遇到 TypeError: Cannot create a consistent method resolution order (MRO) 错误时，底层根本原因是什么？

#### 🎯 面试官考点
- C3 线性化冲突判定、继承拓扑环路排查。

#### 💡 满分回答模板
1. **错误触发根因**：
   - 当开发者定义的继承关系**直接违背了 C3 算法的“单调性”或“局部优先级”**，导致拓扑排序算法在 Merge 阶段陷入无法决议的死锁；
2. **经典复现案例（次序冲突）**：
   ```python
   class X:
       pass


   class Y(X):
       pass


   class Z(X, Y):
       pass  # ❌ 抛出 TypeError: Cannot create a consistent MRO
   ```
   - **冲突分析**：
     - 根据类 Y 的继承关系：Y 继承 X，说明 **Y 必须排在 X 之前**（`[Y, X]`）；
     - 根据类 Z 的声明 `Z(X, Y)`：括号顺序声明了 **X 必须排在 Y 之前**（`[X, Y]`）；
     - 两者产生不可调和的逻辑悖论，C3 算法检测到无法打破的环路冲突，立即阻断类的创建。
3. **排查解法**：调整子类声明中基类的书写顺序，确保从具体子类到抽象父类的演进次序一致。
