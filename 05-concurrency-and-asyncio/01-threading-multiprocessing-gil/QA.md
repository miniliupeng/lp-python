# 大厂高频面试题精讲 (04-01-threading-multiprocessing-gil)

---

### Q1: 请详述 Python 的 GIL（全局解释器锁）的本质原因与影响。为什么在现代多核 CPU 时代它依然存在？

#### 🎯 面试官考点
- CPython 虚拟机线程安全性设计、引用计数锁开销与历史生态向后兼容性。

#### 💡 满分回答模板
1. **GIL 的底层定义与本质原因**：
   - GIL（Global Interpreter Lock）是 CPython 解释器中用于保护内部数据结构和内存引用的**互斥锁（Mutex）**；
   - **根本成因**：CPython 内存管理重度基于**引用计数（`ob_refcnt`）**。如果在多线程中并发修改引用计数，除非为每个 Python 对象的自增自减都加细粒度锁（这会导致严重的死锁和单线程性能暴跌 30% 以上），否则内存必将损坏；CPython 权衡后选择了最直接粗暴的方案：用一个全局大锁互斥所有字节码执行。
2. **为什么迟迟未能移除（生态枷锁）**：
   - **单线程性能不妥协原则**：Python 社区要求任何移除 GIL 的提案，**绝不能让单线程代码执行速度变慢**；
   - **庞大的 C 扩展生态**：NumPy、SciPy 等海量底层 C 扩展在编写时默认假设了 GIL 的存在，直接去锁会导致整个科学计算与 AI 生态彻底崩溃。

### Q2: I/O 密集型任务与 CPU 密集型任务，在多线程与多进程选型上有何本质不同？各自有哪些内存与通信代价？

#### 🎯 面试官考点
- 进程与线程的操作系统资源开销（虚拟地址空间、页表、IPC）、并发架构精准选型。

#### 💡 满分回答模板
1. **CPU 密集型（首选 `multiprocessing` 多进程 / Celery）**：
   - **机制**：每个进程拥有完全独立的 CPython 解释器实例、独立的堆内存与独立的 GIL，能够被操作系统无障碍分发到不同的物理 CPU 核心真正并行运算；
   - **代价**：进程启动慢、内存占用大（每个进程基础常驻数十 MB）；跨进程传递数据必须通过 **IPC（管道/套接字）进行序列化与反序列化（Pickle）**，通信成本极高。
2. **I/O 密集型（首选 `asyncio` 异步协程，其次多线程）**：
   - **机制**：当进行网络读写或磁盘等待时，底层会自动释放 GIL；
   - **选型权衡**：
     - 多线程共享进程内存，通信方便，但每个线程默认独占数 MB 栈内存，线程数达到数千个时系统上下文切换将引发雪崩；
     - **`asyncio` 协程在单线程内运行**，协程上下文切换完全发生在用户空间（无内核态开销），内存占用仅几 KB，是现代高吞吐 Web 服务的首选基石。

### Q3: Python 3.13+ 引入的 PEP 703（Free-threaded 无 GIL 模式）底层做了哪些核心革新？去 GIL 会带来哪些代价？

#### 🎯 面试官考点
- 2026 前沿版本演进、Mimalloc 内存分配器优化、偏向引用计数（Biased Reference Counting）。

#### 💡 满分回答模板
1. **三大核心底层革新**：
   - **偏向引用计数（Biased Reference Counting, BRC）**：
     将引用计数拆分为两个字段：创建对象的“属主线程”可以无锁快速更新本地计数；只有其他线程访问时才使用昂贵的原子指令（Atomic Operations），大幅降低了常规访问开销；
   - **永久对象（Immortal Objects, PEP 683）**：
     将小整数、字符串常量、内置类型等全局单例标记为“永久存活”，引用计数完全不变更，避免跨线程缓存失效；
   - **Mimalloc 分配器深度集成**：采用微软的极速内存分配器实现线程安全的内存切片并发分配。
2. **代价与现状**：
   - 单线程性能在目前阶段仍有约 5%~10% 的轻微损耗；
   - C 扩展库需要逐步重构兼容自由线程标记，目前作为可选编译模式在生产中逐步推广。
