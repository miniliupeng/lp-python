# 专题 04：垃圾回收机制、三代收集算法与弱引用 weakref 实践

内存管理是后端常驻进程的生命线。CPython 采用了**以“引用计数（Reference Counting）”为主、以“分代垃圾回收（Generational GC）”为辅**的复合垃圾回收架构，兼顾了内存即时释放的确定性与对复杂循环引用（Cyclic References）的兜底回收。

---

## 一、 痛点驱动：引用计数的致命死锁——循环引用

1. **孤岛循环引用导致的永久内存泄漏**：
   - 对象 A 内部引用了对象 B（`a.b = b`），同时对象 B 也引用了对象 A（`b.a = a`）；
   - 外部调用 `del a; del b` 删除局部变量后，两者的引用计数均只能递减到 1，而绝不可能变为 0！
   - 结果：外界已经没有任何途径可以访问这两个对象，但由于引用计数不为 0，它们永远无法被释放，形成**内存泄漏孤岛**。

---

## 二、 机制解密：三代回收算法与三色标记

```text
CPython 内存管理双轮驱动:
  1. 引用计数机制 (主战武器，实时递减至 0 瞬间释放)
         │ (若存在循环引用无法归零)
         ▼
  2. 分代收集引擎 (gc 模块，周期性排查并回收循环孤岛)
     ├── 第 0 代 (Young): 新分配对象，GC 触发最频繁 (阈值 700)
     ├── 第 1 代 (Middle): 经历 1 次 GC 存活晋升
     └── 第 2 代 (Old): 长期存活对象 (单例/模块)，GC 触发频率极低
```

1. **分代假说（The Generational Hypothesis）**：
   - 绝大多数对象寿命极短（“朝生夕死”，如局部变量）；少数存活下来的对象生命周期往往很长。针对新生代进行高频轻量扫描，大幅降低全堆停顿；
2. **破环利器：弱引用（`weakref`）**：
   - 弱引用允许引用一个对象，但**绝对不增加该对象的 `ob_refcnt`**；
   - 当真实对象由于外部没有强引用被析构时，弱引用会自动失效并返回 `None`，从物理层面彻底扼杀循环引用的产生条件。

---

## 三、 生产规范与最佳实践

- **缓存与观察者模式必用 `weakref`**：缓存字典禁止持有强引用，推荐使用 `weakref.WeakValueDictionary`；
- **排查生产内存泄漏**：利用 `gc.get_objects()` 与 `tracemalloc` 模块捕获堆快照，比对未释放的对象增长曲线。
