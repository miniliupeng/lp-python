# 大厂高频面试题精讲 (01-04-garbage-collection-and-gc)

---

### Q1: 请详述 CPython 垃圾回收的三大机制：引用计数、标记清除与分代回收（Generational GC）。

#### 🎯 面试官考点
- CPython 内存回收全景体系、优劣势互补与核心算法流转。

#### 💡 满分回答模板
1. **第一支柱：引用计数（Reference Counting，主干机制）**：
   - 每个对象维护 `ob_refcnt`。当有新指针指向它时 +1，指针移除或出栈时 -1；
   - **优势**：当计数归 0 时，**内存被立即实时释放**，没有延迟，无全堆扫描停顿；
   - **致命缺陷**：无法回收互相引用的孤岛环路。
2. **第二支柱：标记清除（Mark-Sweep，辅助机制）**：
   - 专门用于处理由容器对象（list, dict, 自定义类等可嵌套类型）构成的环形引用；
   - 算法在不可达判定阶段：将活动链表中每个容器对象的引用计数预先扣除它们内部对彼此的引用；如果扣除后某个对象的引用计数降为 0，说明外界已无指针指向该环路，标记为垃圾并予以清除。
3. **第三支柱：分代回收（Generational Collection，性能调优引擎）**：
   - 引入 0 代、1 代、2 代三级分层；
   - **分代假设**：存活时间越长的对象越不易消亡。新创建对象放入 0 代，当经历一轮 GC 仍存活时晋升入 1 代，以此类推；
   - 0 代触发阈值最低、检查最频繁；2 代检查最少，从而将 GC 停顿时间（Stop-the-World）控制在极低范围。

### Q2: 为什么在 Python 3.4 之前包含 __del__ 方法的循环引用对象会导致整个垃圾回收器彻底罢工？现代版本是如何解决的？

#### 🎯 面试官考点
- PEP 442 析构器安全演进、终结器（Finalizers）执行顺序与历史陷阱。

#### 💡 满分回答模板
1. **历史严重痛点（Python 3.4 之前）**：
   - 在旧版 Python 中，如果两个处于循环引用的对象都定义了 **`__del__()`** 析构方法；
   - 当垃圾回收器试图回收该环路时，**无法确定应该先调用 A 的 `__del__` 还是先调用 B 的 `__del__`**（因为在 A 的析构中可能需要安全访问 B）；
   - 由于无法安全决议析构顺序，解释器只能把它们扔进全局不可回收列表 `gc.garbage` 中，导致这部分内存**永久泄漏且无法回收**！
2. **现代 PEP 442 解决方案（Safe Object Finalization）**：
   - Python 3.4+ 彻底重写了析构逻辑。垃圾回收器首先切断环中的弱连接，然后再依次安全触发各对象的 `__del__` 方法，彻底解决了带析构函数的循环引用内存泄漏问题。
   - **生产规范**：虽然现代 Python 已修复此问题，但生产中仍强烈建议使用 `with` 上下文管理器来显式释放网络/文件句柄，而非依赖不确定的 `__del__`。

### Q3: 什么是弱引用（Weak Reference）？在缓存系统或观察者模式中如何利用 weakref 防止内存泄漏？

#### 🎯 面试官考点
- 弱引用底层原理、`weakref` 模块与缓存防 OOM 设计。

#### 💡 满分回答模板
1. **弱引用的底层本质**：
   - 弱引用是对目标堆对象的非排他性代理，**它绝不增加目标对象的 `ob_refcnt` 引用计数**；
   - 目标对象的 `PyTypeObject` 维护了一个弱引用链表头。当该对象真实引用归 0 发生析构时，解释器会自动遍历该链表，将所有指向该对象的弱引用指针置空（或触发注册的清理回调）。
2. **生产实战：防止全局缓存引发 OOM 爆炸**：
   - **反例**：用普通的普通字典做缓存（`cache[key] = obj`），由于字典持有对象的强引用，只要该键未被手动删除，所有被缓存的对象将永远无法被垃圾回收，导致内存持续飙高直至崩溃；
   - **正解**：使用 **`weakref.WeakValueDictionary`**。外部代码持有真实对象；一旦外部代码放弃引用，缓存字典内部会自动清理该键值对，做到无缝按需释放，天然杜绝缓存内存泄漏。
