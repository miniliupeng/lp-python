# 专题 03：pytest 现代单元测试套件、参数化与 Fixture 依赖注入

软件工程的交付底线是自动化测试。相比 Python 原生继承自 Java xUnit 体系的冗长 `unittest`，现代工业界几乎 100% 选用 **`pytest`**。pytest 凭借原生 `assert` 表达式重写、强大的 **`fixture` 依赖注入图** 以及 **`@pytest.mark.parametrize`**，提供了极具表现力且严谨的测试底座。

---

## 一、 痛点驱动：传统 unittest 的历史包袱

1. **强耦合 OOP 继承与样板代码爆炸**：
   - `unittest` 强制所有测试类必须继承自 `TestCase`，测试方法必须以 `test_` 开头，且必须记忆 `assertEqual`、`assertRaises` 等数十个专用断言 API；
2. **前置清理机制僵硬（Setup/Teardown 缺陷）**：
   - 依赖固定的 `setUp()` / `tearDown()`，无法在多个测试类之间复用细粒度测试上下文，容易产生全局状态泄漏；
3. **缺少优雅的参数化数据驱动测试**：
   - 针对一个函数的十几种边界用例，传统方式只能写冗长的循环或复制多个测试用例，一旦中间某项断言失败，后续用例将直接被阻断终止。

---

## 二、 机制解密：AST 断言重写与 Fixture DAG 依赖注入

```text
[ pytest 执行链路 ]
 ├── AST 导入钩子 (Import Hook) ──> 动态重写原生 assert 表达式 (精准提取左右变量上下文)
 └── Fixture 拓扑解析引擎 ────────> 构建有向无环图 (DAG)，自动执行依赖注入与 yield 析构
```

1. **原生 `assert` 魔法（AST Rewriting）**：
   - pytest 在模块加载阶段通过 Python 导入钩子（Import Hook），动态拦截并**重写测试文件中的 `assert` 语句字节码**。当断言失败时，它能像调试器一样精准打印出表达式中每个变量的实时计算快照；
2. **Fixture 的依赖注入与声明式生命周期**：
   - 测试函数通过在参数列表声明 fixture 名称，pytest 自动分析依赖拓扑并注入实例；
   - 通过在 fixture 中使用 **`yield`**，前半部分作为初始化 Setup，`yield` 后的代码作为测试结束后的自动化清理 Teardown，即使测试中途崩溃也能确保外部连接与临时资源被安全释放。

---

## 三、 生产规范与最佳实践

- **保持单次断言针对性**：一个测试用例尽量只验证一个具体业务行为；
- **善用参数化覆盖边界**：使用 `@pytest.mark.parametrize` 覆盖正常输入、零值、极限值、异常逆向测试；
- **禁止在测试中建立真实外部网络连接**：数据库使用内存 SQLite 或事务回滚，外部 HTTP 调用必须通过 Mock 隔离。
