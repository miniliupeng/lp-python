# 大厂高频面试题精讲 (02-modern-pyproject-and-toolchain)

---

### Q1: 为什么现代 Python 全面废弃了 setup.py / requirements.txt 而统一推崇 pyproject.toml？

#### 🎯 面试官考点
- Python 打包构建生态演进史（PEP 517/518/621）、供应链安全（动态代码执行漏洞）与标准化元数据。

#### 💡 满分回答模板
1. **安全性根治（消除任意代码执行）**：
   - 传统的 `setup.py` 是可执行的 Python 脚本，这意味着在解析包元数据或下载依赖时必须执行远程代码，曾多次被黑客利用发起供应链挖矿与投毒攻击；
   - `pyproject.toml` 是纯声明式的静态文本配置文件，无需执行任何 Python 代码即可被安全的构建引擎解析。
2. **统一单一真理来源（Single Source of Truth）**：
   - 过去项目元数据分散在 `setup.py`（打包）、`requirements.txt`（依赖）、`setup.cfg`（工具配置）等处，极易产生配置冲突与不同步；
   - PEP 621 统一定义了 `[project]` 命名空间，使依赖、版本、作者、构建后端全部收敛于一个标准文件。
3. **构建后端解耦（PEP 517/518）**：
   - 允许开发者通过 `[build-system]` 自由声明构建后端（如 `hatchling`, `flit`, `setuptools`, `maturin`），彻底打破了过去对 `setuptools` 的绝对绑架。

### Q2: pyproject.toml 与 lockfile（如 uv.lock）在生产发布体系中各自扮演什么角色？为什么 lockfile 必须纳入版本控制？

#### 🎯 面试官考点
- 抽象依赖声明 vs 确定性环境重现（Deterministic Reproducibility）、语义化版本飘移风险。

#### 💡 满分回答模板
1. **定位与职责分工**：
   - **`pyproject.toml`（面向人类与抽象约定）**：声明的是**直接依赖的合理兼容区间**（例如 `fastapi>=0.115.0,<1.0.0`），保留未来升级补丁版本的灵活性；
   - **`uv.lock`（面向机器与确定性构建）**：记录的是经过解析后全量依赖树（包含直接依赖和所有深层传递依赖）的**精确具体版本号与文件内容哈希值（Sha256）**。
2. **纳入版本控制的决定性理由**：
   - **杜绝依赖飘移（Dependency Drift）**：如果不提交 lockfile，当某个传递依赖库发布了一个破坏向后兼容性的紧急小版本时，CI/CD 流水线构建出的线上环境将瞬间崩溃，导致出现“昨天测试还是好的，今天上线直接宕机”的灾难事故；
   - **保障构建确定性与防篡改**：结合内容哈希校验，防止依赖包在远程镜像源被恶意篡改。

### Q3: Ruff 是如何利用 Rust 和 AST 遍历在单次遍历中完成代码 Lint 与 Formatting 的？

#### 🎯 面试官考点
- 编译原理前端实现、AST 抽象语法树优化与工业级工程效能提升思路。

#### 💡 满分回答模板
1. **底层语言性能代差**：
   - 传统工具（Flake8/Black）基于 Python 编写，受 GIL 和大量中间对象内存分配的性能拖累；Ruff 采用 Rust 编写，具备极高的并发调度能力与零成本抽象内存模型。
2. **单次 AST 遍历流水线（Single-pass Optimization）**：
   - 传统工作流：运行 Flake8 解析一遍 AST 生成警告；运行 isort 再次解析 AST 排序导入；运行 Black 再次生成格式化语法树。多次解析带来巨大无谓开销；
   - Ruff 在内存中建立起统一的抽象语法树（AST）与词法 Token 流，在**单次树遍历中并发应用数十条规则**，同时产出错误诊断与代码修改指令，从而实现数十倍甚至上百倍的性能飞跃。
