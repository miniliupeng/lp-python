# C04　字节码与解释器

> 示例：`examples/part_c/c04_bytecode.py`

## 学完你能做什么

用 `dis` 看懂一个函数被编译成了哪几类指令，并拒绝背一条“所有版本都一样”的字节码清单。

## 虚拟机执行指令

CPython 的求值循环取出 `co_code` 里的指令执行。`dis.get_instructions` 把它们还原成名字。示例的 `add` 至少包含：

- `LOAD_FAST`：从帧的局部变量槽取出 `left` 或 `right`。
- `BINARY_OP`：做加法。3.11 之后二元运算多用这一条带参数的指令，而不是旧资料里的 `BINARY_ADD`。
- `RETURN_VALUE`：把栈顶的值返回给调用者。

3.12 上这个函数的指令列表现在就是这些，加上 `RESUME` 之类的前缀。3.13、3.14 可能增删专门化指令。示例不断言完整列表，只断言这三类还在。面试里如果有人拿出一条 opcode 当永恒事实，让他在目标版本上 `dis.dis` 一次。

## 求值栈

字节码是栈式的。`LOAD_FAST` 把值压栈，`BINARY_OP` 弹出两个操作数、压入结果。`co_stacksize` 是编译器算出的最大栈深。这不是操作系统线程的 C 栈，那是另一件事。递归消耗的主要是帧，帧里才放着这个求值栈。

局部变量用下标访问，所以一般比全局名字查找快。全局名字在 `co_names` 里，运行时要在全局字典中查找，尽管 3.11 的自适应解释器会把热点指令专门化，缩小这种差距。差距的大小以测量为准，C09 讲怎么量，这里不给一个虚假的百分比。

## 自适应特化

PEP 659 从 3.11 起给字节码加了特化。例如加法看过几次都是整数之后，可以走更快的整数路径，类型变了再退回通用路径。所以“Python 永远按最通用的对象协议做加法”对冷代码大致成立，对热代码不是完整描述。

这不影响语义。整数加整数仍然是整数加整数。它影响的是你在 `dis` 里看到的指令名字可能带 `SPECIALIZED` 之类的信息，以及性能随运行过程变化。微基准如果只跑一次，看到的是还没热起来的解释器。

## 编译器会先算掉的东西

字面量计算可能在编译期折掉。`250 + 7` 出现在函数源码里，字节码里可能只剩常量 `257`。这就是 C02 说的常量合并的来源。想看运行时的加法，把操作数放进变量，示例的 `add` 就是这么做的。

## 看字节码的正当用途

- 确认一个名字是局部还是全局。
- 确认某段代码有没有在循环里做属性查找。
- 理解为什么两个写法的栈行为不同。

不正当用途：把某次 `dis` 的输出当生产代码生成，或者用 `eval` 拼接字节码。需要动态执行时，优先是函数和类。`eval` 和 `exec` 执行字符串，那是另一个巨大的注入面，D08 会拒绝把它当配置方案。

## 机制

CPython 虚拟机执行代码对象里的字节码。指令从求值栈取操作数，再把结果压回去。`dis.dis` 能反汇编。指令名在 3.11、3.12、3.13 之间变过，专门化指令还会在运行中替换。所以字节码是观察工具，不是稳定 API。

3.11 的自适应特化（PEP 659）会把热的 `LOAD_ATTR` 一类指令换成更快的专门版本，发现类型变了再退回。这是解释器内部的优化。你的代码不需要为它改写法。

编译器会做少量常量折叠。纯常量的加法可能在编译期就算进常量表。因此“我在源码里写了加法，字节码里一定有 `BINARY_OP`”不一定成立。要以 `dis` 的实际输出为准，并且标明解释器版本。

看字节码的正当用途：理解局部变量为什么比全局查找少一次字典查找、理解 `+=` 是多条指令所以不是原子的、理解推导式生成了嵌套的代码对象。不正当用途：背 opcode 应付面试、根据某次 `dis` 输出写“性能规范”。

默认构建下，线程要执行 Python 字节码必须持有 GIL。一条纯字节码执行过程中，通常不会让另一条线程跑 Python 字节码；阻塞 I/O 的 C 调用会主动放开 GIL。一个 Python 语句仍然常常是多条字节码。`counter += 1` 因此要自己的锁。这是 C05 的主题，字节码只负责说明“语句不是原子的”。自由线程构建不遵守“同时只有一条线程执行字节码”这一条。

3.13 起的 JIT 是拷贝-补丁实验。默认不开。不要把 `dis` 的输出说成机器码。

## 会出事的写法

- 在生产代码里依赖某条 opcode 的存在。升级补丁版本就可能变。
- 用 `eval` 加拼出来的源码只为了少写一个函数。编译和执行用户字符串是注入。
- 为了“减少字节码”把程序写成一行。可读性损失远大于少一次查找。
- 在热路径上反复 `dis` 或 `compile`。那是诊断，不是请求处理。

## 示例对照

`examples/part_c/c04_bytecode.py` 用 `dis` 或代码对象的属性做稳定断言：例如常量在 `co_consts` 里，函数有 `__code__`。不要断言完整的字节码字符串，那会在小版本升级时碎掉。如果示例检查某条指令名，应锁定在 3.12 并在注释里说明。

## 加练

1. 为什么 `counter[0] += 1` 在有 GIL 时仍可能丢更新？请用“多条字节码”回答，不要测量时间。
2. 常量折叠会给微基准带来什么假象？

参考答案：

1. 读取、相加、写回是多条指令。GIL 可能在两条指令之间让出。另一条线程读到旧值再写回，更新丢失。锁把这几条指令包成临界区。
2. 你以为在测循环里的加法，编译器可能已经把纯常量算掉了。微基准要使用运行时才知道的值，并看 `dis` 确认循环里还有运算。

## 面试

### Q1. 为什么不要背 opcode？

**考点**：稳定接口和观察工具的差别。

**回答**：

1. 字节码随版本变化，3.11 以后还有运行期特化。
2. 业务正确性由语言参考定义，不由某次 `dis` 定义。
3. `dis` 适合解释“这条语句不是原子的”或“这个名字是局部的”。结论要用语言规则复述出来。

### Q2. 自适应特化改变了语言语义吗？

**考点**：优化必须保持语义。

**回答**：

1. 不改变。特化失败会退回通用指令。
2. 它利用的是运行中观察到的类型。类型变了就失效。
3. 你不需要为了特化去给局部变量加注解。注解不是给这个优化器用的。

### Q3. `eval` 和函数调用在执行模型上差在哪？

**考点**：编译用户输入的危险。

**回答**：

1. 函数已经编译成代码对象，调用只是新的一帧。
2. `eval` 和 `exec` 对字符串再做解析和编译，而且能访问传入的命名空间。
3. 用户输入进 `eval` 就是代码注入。配置和表达式如果真要计算，用限定过的解析器，而不是把内建函数交出去。

## 常见错误

- 背 `BINARY_ADD`。3.12 的这个函数里没有它。
- 认为看懂字节码就能判断服务的瓶颈。瓶颈可能在数据库。先测量整条请求，再决定要不要看指令。
- 把 `dis` 输出贴进文档还不写 Python 版本。指令表是版本的一部分。

## 练习

1. 对一个读取全局变量的函数做 `dis`，找出和 `LOAD_FAST` 不同的加载指令名。
2. 为什么示例不比较 `dis.Bytecode(add).dis()` 的完整文本？
3. 自适应特化改变语言语义吗？

参考答案：

1. 你会看到 `LOAD_GLOBAL`（具体名字以 3.12 的输出为准）。把一个模块级名字放进函数里读取即可。
2. 完整文本随版本和专门化变化。教程只锁定语义需要的那几类指令。
3. 不改变。它只选择更快的实现路径，类型对不上就回退。

## 小结

CPython 执行字节码，局部变量用 `LOAD_FAST`，运算在求值栈上完成。指令名会变，3.11 起还有自适应特化。用 `dis` 理解结构，不用它背诵实现。
