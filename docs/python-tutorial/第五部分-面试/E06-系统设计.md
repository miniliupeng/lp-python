# E06　系统设计题

> 对照示例：`examples/part_e/e06_design.py`。回答时先讲不变量和失败行为，再讲组件。示例只固定 LRU 的淘汰结果，避免把分布式系统假装成一个函数。

### 1. 设计短链服务，你先说哪几句？

**常见错法：** 用随机 6 位字符，存在一个全局字典里，读的时候 O(1)，结束。

**回答：** 内部用不可猜测性以外的方式保证唯一，例如数据库序列或发号器，再编码成短字符串。编码可逆不等于保密，私密目标仍要鉴权。原始 URL 在写入时校验。唯一约束放在存储上，避免“先查再插”的空窗。重定向要有缓存时，缓存失效不能把用户带到错误地址。Python 进程可以无状态地编码和解码，事实存在数据库里。多进程不要共用一个没有同步的内存字典当发号器。

### 2. 令牌桶和固定窗口怎么选？

**常见错法：** 限流就是每分钟一个整数，加锁加一。

**回答：** 固定窗口实现简单，窗口边界可能放进近两倍配额。令牌桶允许容量以内的突发，按速率恢复。漏桶更接近匀速。要说清状态放在进程内还是共享存储。进程内状态乘以副本数才是全集群的真实限额。拒绝用 429，并给出重试间隔。测试时把时间当参数，不睡眠。示例所在的 D10 用注入时钟把这个策略测完了。

### 3. LRU 缓存的淘汰和一致性？

**常见错法：** 缓存和数据库总会一样，因为每次写入都记得去改缓存。

**回答：** 容量满时丢掉最久没有被访问的键。示例容量为 1，写入 `b` 之后 `a` 必须消失。缓存不是事实来源。写成功后删除键，或使用版本。只用 TTL 就要接受过期前的旧值。穿透是不存在的键反复打到数据库，可以短 TTL 缓存否定结果。击穿是热键刚好失效时被同时回源，需要合并或互斥。雪崩是大量键同时失效或缓存进程重启，TTL 要加抖动，数据库要扛得住冷启动。

### 4. 任务队列怎样承诺投递？

**常见错法：** 我们的队列是恰好一次，因为用了 Redis。

**回答：** 至少一次要求消费者幂等，用幂等键记下已经完成的任务。至多一次可能丢。恰好一次需要事务性的出队和结果保存，不能只靠口头承诺。任务体是数据不是代码。失败有次数上限，超过后进死信。队列有上限，满了就拒绝生产者，而不是无限长。CPU 密集的工作者在默认 GIL 下用进程。

### 5. 怎样设计一个会扣库存的接口？

**常见错法：** 读出数量，在 Python 里减一，写回去。失败就重试整个请求。

**回答：** 不变量是库存不为负。在一个事务里用条件更新：只有当前数量足够才减少，影响行数为 0 就返回库存不足。先读后写会丢更新。请求带幂等键，重试不会扣两次。缓存里的库存数字只能当展示，下单以数据库条件更新为准。B13 的内存模型是这个不变量的单线程版，D06 补上事务。

### 6. API 水平扩展时，哪些状态会绊住你？

**常见错法：** Python 服务无状态，开更多副本就线性变快。

**回答：** 代码无状态才可以水平扩展。进程内存里的限流计数、会话、缓存、后台线程，都不会自动共享。会话放进共享存储或做成签好名的令牌。缓存和限流如果在进程内，要接受“每个副本一份”的语义。数据库连接池要有上限，副本数乘以池大小就是数据库看到的连接数。CPU 密集任务不要和请求处理抢同一个默认解释器的 GIL，拆进程。

### 7. 怎样做优雅关闭？

**常见错法：** 杀掉进程，客户端会自动重试，所以数据不会有问题。

**回答：** 收到 `SIGTERM` 后停止就绪检查，负载均衡不再送新请求。停止拉取新任务，把已接收的请求处理完，事务结束，再退出。客户端重试只对幂等操作安全。处理器里只设标志。给关闭一个时限，超时才强制退出。

### 8. 读写缓存和数据库不一致时，用户应当看到什么？

**常见错法：** 永远强一致，延迟也和只读缓存一样。

**回答：** 先选择。读已写入的自己的数据，可以绕过缓存或使用版本。别人的时间线若允许秒级延迟，TTL 和异步失效就够。不要在设计开头承诺强一致，实现却是“更新数据库后异步删缓存，失败就不管”。删缓存失败要有补偿或可重试的失效消息。

### 9. 分页为什么不能只做 `OFFSET`？

**常见错法：** `OFFSET` 越大只是数字变大，成本不变。

**回答：** 大偏移量会让数据库丢掉前 N 行，成本随页码上升。数据还有插入时，偏移分页会重复或漏掉。稳定排序键上的“查比上一页最后一条更大的记录”更稳。接口要有最大 `limit`。没有上限的列表最终会变成内存问题。

### 10. 设计一个上传文件的接口，安全上先拒绝什么？

**常见错法：** 用用户提供的文件名拼到上传目录，扩展名合法就保存。

**回答：** 文件名不直接当路径。生成存储名，原始名只做展示字段。路径解析后必须留在根目录内。限制大小和类型，类型不要只看扩展名。病毒扫描和内容识别是额外的产品要求，至少先把大小、路径和权限做对。元数据进数据库，字节进对象存储或受控目录。不要把上传内容送进 `pickle` 或模板执行。

### 11. 怎样观察这个系统？

**常见错法：** 出问题再登录机器打印全局变量。

**回答：** 每个请求有请求号，日志能串起来。指标至少有请求速率、错误率、延迟和队列长度。追踪跨进程时继续传递同一个标识。告警对着用户能感到的症状，而不是对着一次 GC 次数。没有请求号的日志在多副本上几乎无法排查。

### 12. Python 在这张图里具体跑什么？

**常见错法：** 用 Python 是因为 GIL 已经不存在，一个进程能吃满所有核。

**回答：** 默认构建仍有 GIL。Python 适合 I/O 型 API、编排和业务规则。CPU 热路径用进程、扩展模块，或在确认依赖支持后评估自由线程构建。JIT 到 3.15 仍是实验开关。设计文档写明当前进程是哪种构建，而不是写“Python 3.15”。

### 13. 限流放在网关还是应用内？

**常见错法：** 两处都写一套不同的限额，谁先生效无所谓。

**回答：** 网关适合按调用方、IP 或路由做粗粒度保护，挡住明显的洪水。应用内适合按业务资源限额，例如每个账号的下单次数，因为只有应用知道资源是什么。两处可以同时存在，但配额的含义要不同，避免用户看到两个互相矛盾的 429。状态仍然要说明是不是全局的。

## 展开

### 短链

1. 先定合同：命中如何重定向，未命中是 404，允许哪些 scheme。
2. 存储是事实来源。缓存只加速热点。点击统计失败不能让跳转失败。
3. 短码要考虑冲突和可猜测性。开放跳转比哈希函数更先被问倒。

### 限流

1. 固定窗口简单，边界会放进约两倍流量。令牌桶允许突发，平均速率由补充速率决定。
2. 计数放进程内时，副本数会乘上限。全局限制要共享存储。
3. 存储故障时失败开放还是失败关闭，必须事先定。

### 缓存和库存

1. 允许旧的读模型要写明延迟。余额和库存不要先改缓存。
2. 扣库存用条件更新：`WHERE qty >= ?`，看影响行数，放在一个事务里。
3. LRU 只解决容量。跨进程失效要另做。键必须包含全部影响结果的参数。

### 队列

1. 至少一次投递要求消费者幂等。
2. 可见性超时要大于处理时间，否则双消费。
3. 入队和业务写入要有同一套恢复故事：外盒表或事务性发件箱。失败进死信，不要无限重试。

### 流式和工具

1. SSE 用 `text/event-stream`，事件以空行分隔。客户端断开要停掉生成。
2. 模型只提议工具调用。宿主校验白名单和参数。不要执行模型给出的 SQL。
3. MCP 统一发现和调用的形状，不代替用户权限。工具返回值仍按不可信输入解析。

### 加练

1. 分页为什么不能只做很大的 `OFFSET`？
2. 上传文件先拒绝什么？

参考答案：

1. 大偏移量要扫描并丢掉前面的行，越翻越慢。用稳定的排序键做“大于上一页最后一条”的条件。还要处理插入导致的重复和遗漏，并写进合同。
2. 大小上限、路径不出根、内容类型白名单、不要按用户提供的文件名直接写到下载目录。病毒扫描和权限是下一步，但没有大小上限就会先被打满磁盘。
