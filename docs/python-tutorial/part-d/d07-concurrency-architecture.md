# D07　并发架构

> 示例：`examples/part_d/d07_concurrency_architecture.py`

## 学完你能做什么

用有界队列表达背压，用哨兵停止消费者，并把超时和取消说成结构设计而不是事后补的 `sleep`。

## 队列划分主人

多个线程一起改 `Stock` 的字典，不变量会坏。更稳的结构是：只有一个工作者执行 `apply`，其他人把 `Movement` 放进队列。数据的主人只有一个。C05 的锁适合保护很短的计数；一长串业务规则更适合串行化到一个主人那里。

`queue.Queue` 是线程安全的移交点。示例先证明 `maxsize=1` 时，第二次 `put_nowait` 抛 `queue.Full`。这就是背压：生产者看到拒绝，而不是无限堆积把内存吃完。阻塞的 `put` 则会让生产者等。两种都是策略。无限队列不是背压，是把问题推迟到内存耗尽。

网络服务里的背压要能传到客户端：拒绝新任务、返回 429 或让调用方重试。只在内部堵住、外面还继续接收，连接一样会堆满。

## 停止

示例用一个专用的 `STOP` 对象当哨兵。消费者看到它就退出。不要用 `None` 当哨兵，除非队列里的合法数据永远不可能是 `None`。专用对象用 `is` 判断，不会和整数任务混淆。

工作者在 `finally` 里 `task_done`。如果有人在 `join` 队列，漏掉 `task_done` 会永远等下去。示例没有 `join` 队列，而是 `join` 线程。两条路都可以，不要混用到计数对不上。

主线程必须 `join` 工作者。守护线程会在进程退出时被切断，队列里的最后一项可能没处理完。

## 超时

任何等待都要有上限：`queue.get(timeout=...)`、HTTP 客户端的 timeout、锁的获取。没有上限的等待会变成“服务还活着但不再前进”。超时之后的失败要可见，记日志并返回错误，不要空转重试。

重试只对可能短暂失败的操作有意义，并且要有次数上限和间隔。间隔不要所有客户端同一秒醒来。幂等的操作才可以安全重试：扣库存如果没有幂等键，重试会扣两次。幂等键是调用方给的唯一编号，服务端记下“这个编号已经做过”，再来就返回上次的结果。

## 取消

协程的取消是 C06 的 `CancelledError`。线程没有同等可靠的强制取消。线程的取消通常是设一个事件，让它在下一次循环自己退出。不要 `Thread._stop` 之类的私有手段。进程可以用进程组的信号，D09 只演示应用自己的关闭标志，不在示例里向自己发信号。

## 常见错误

- 无界队列加上比消费者更快的生产者。
- 多个工作者不持锁地改同一份账，还以为队列已经让他们安全。队列保证的是移交，不是“出队之后可以随便共享可变对象”。出队后的对象如果只有这个工作者使用，才是安全的。
- 超时后立刻无间隔重试，把下游打得更满。

## 练习

1. `maxsize=1` 且已经有一项时，`put_nowait` 发生什么？
2. 为什么哨兵是 `object()` 而不是 `0`？
3. 重试扣款之前，调用方必须提供什么？

参考答案：

1. 抛 `queue.Full`。队列不会为了这次放入而扩容。
2. `0` 可能是合法任务。新创建的 `object()` 只和自己 `is` 为真。
3. 幂等键，或者服务端能识别“同一请求”的其他稳定标识。否则重试会重复扣款。

## 小结

用队列把共享可变状态收成一个主人。队列要有上限，停止要用专用哨兵，等待要有超时。重试必须有上限，并且只作用在幂等操作上。
