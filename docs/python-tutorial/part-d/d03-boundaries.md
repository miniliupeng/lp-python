# D03　边界上的类型与校验

> 示例：`examples/part_d/d03_boundaries.py`

## 学完你能做什么

把“注解”“结构协议”“运行时解析”放在三层里，不再指望其中一层干另外两层的活。

## 三层

1. **注解和类型检查器。** 在开发时看调用是否对得上。它们不随进程部署，除非你另外部署了一个检查步骤。B09 已经说明运行时不自动校验。
2. **`Protocol`。** 描述“有这些方法即可”，用来给检查器看结构类型。`@runtime_checkable` 让 `isinstance` 能做一次很浅的判断：属性在不在。示例里 `Person` 有 `greet`，所以它是 `Greeter`。这个检查不读 `greet` 的参数类型，也不调用它。它挡不住一个 `greet` 方法其实需要两个参数的对象。运行时协议检查是辅助，不是验证器。
3. **边界解析。** 外部来的文本、JSON、环境变量，在进入系统时变成内部类型。失败就拒绝。`parse_port` 只接受 `1` 到 `65535` 的整数。`"http"` 和 `"70000"` 都失败。通过之后，内部函数的参数就是 `int`，不必每个函数再解析一遍字符串。

内部函数信任内部类型。这个信任来自边界只有少数几个，并且都测过。到处 `isinstance` 说明边界没有守住。

## 解析要保留原因

`int(text)` 失败时的 `ValueError` 可以变成你自己的配置错误，用 `raise ... from` 留下数字格式不对这个原因。示例为了短，让 `int` 的异常直接冒出，端口范围则抛出带明确消息的 `ValueError`。生产代码里，配置错误应当指出变量名，例如 `PORT`，而不是只说“invalid”。

不要在解析失败时返回 `None` 再让调用方忘记判断。失败是异常或一个明确的结果类型。如果两种失败都用 `None`，调用方无法区分“没配置”和“配置错了”。

## JSON 和字典

`json.loads` 给出 `dict`、`list`、`str`、`int`、`float`、`bool`、`None`。它不给出你的 dataclass。边界上写一个函数，从字典取出字段、检查类型、构造 `Movement` 或 `Point`。缺字段、类型不对，都在这个函数失败。

3.15 的 `frozendict` 不是 `dict` 的子类。如果边界打算接受它，按 C07 的方式检查 `Mapping`，再仍然构造你自己的内部对象。内部状态不必保留外部的容器类型。

## 常见错误

- 用 `runtime_checkable` 代替解析。方法存在不代表 JSON 字段合法。
- 在业务中层捕获所有 `ValueError` 再返回默认端口。调用方会在错误配置下悄悄连到 8000。
- 注解写了 `int`，HTTP 查询参数却仍然是字符串，函数里直接做算术。转换发生在视图函数或专门的解析层，不发生在注解里。

## 练习

1. `parse_port("0")` 应当成功吗？看示例的范围。
2. 给 `Person` 增加一个不相关的方法，`isinstance` 结果变不变？
3. 为什么内部的 `Stock.apply` 不再接收字符串形式的数量？

参考答案：

1. 不应当。范围从 1 开始，`0` 抛 `ValueError`。
2. 不变。`runtime_checkable` 只要求 `greet` 存在。
3. 字符串在边界上已经变成正整数和枚举。账本维护的是不变量，不是文本格式。

## 小结

类型检查器看开发期，协议描述结构，解析函数在边界上生产内部对象。`isinstance` 对协议的运行时检查很浅。错误配置要失败，不要变成默认值。
