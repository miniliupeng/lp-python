# D06　持久化与事务

> 示例：`examples/part_d/d06_persistence.py`

## 学完你能做什么

用 SQLite 把一次写入放进事务，用参数把数据传给 SQL，而不是拼进语句。

## 内存库足够说明语义

`sqlite3.connect(":memory:")` 得到只活在这个连接里的数据库。示例创建 `note` 表，在 `with connection` 里插入一行然后抛异常。连接的上下文管理器在异常时回滚，不关闭连接。回滚后行数是 0。成功的 `with` 会提交。

这就是事务的最低承诺：这一组修改要么都在，要么都不在。库存例子里“先算后写”只保护了一次字典赋值。两张表要一起改时，必须放进同一个事务。

SQLite 的锁和隔离级别比这个例子复杂。它适合嵌入式和测试。多写并发很高时，人们会换别的数据库，但“用事务包住不变量”“不要拼接 SQL”不会因此改变。

## 参数化

```python
connection.execute("insert into note(body) values (?)", (payload,))
```

`payload` 是数据，占位符 `?` 是 SQL 结构。示例把一段看起来像 SQL 的文本当正文存进去，表还在，正文原样可读。拼接字符串会让这段文本变成语句的一部分。参数化把这扇门关上。

不要用格式化字符串填表名和列名。占位符不能替换标识符。列名如果真的来自变量，用一份允许的名字白名单去选，然后仍用占位符填值。白名单写在代码里，不来自请求正文。

每个语句的参数个数要和占位符一致。序列参数记得写成一元元组 `(payload,)`，写成 `(payload)` 只是括号，不是元组。

## 连接的生命周期

连接不是每次函数调用都新建再扔掉的一次性杯子，也不是一个无限共享、从不关闭的全局变量。应用程序通常有一个有上限的连接池，请求借用一条，用完归还。泄漏的症状是请求开始等待连接，而不是 Python 异常。

示例的连接在进程结束时一起消失，因为内存库本身就不持久。文件型数据库要在结束时 `close`。`with connection` 不会代你关闭，这和文件对象不同，是标准库里容易记错的一点。

## 迁移

表结构会变。把 `CREATE TABLE` 放在应用启动时随便执行，很快就会和已有数据冲突。迁移是有版本号的脚本：第 1 版建表，第 2 版加列。生产数据库先备份，再按版本升级。教程示例每次都从空库开始，所以把建表写在测试里是合理的，不要把这个习惯搬进一个已有文件的启动代码。

## 机制

事务的承诺是：一组写入要么都留下，要么都不留下。示例用内存 sqlite 把这句话变成断言。`with connection:` 在块正常结束时提交，在块里异常时回滚。它不关闭连接。连接还要显式 `close`，或者用会关闭的封装。这是 sqlite3 的实现选择，和文件的 `with` 不同。

参数化把 SQL 结构和值分开。`execute("insert ... values (?)", (payload,))` 里 payload 是数据，哪怕它看起来像 `drop table`。字符串拼接 SQL 是注入。示例插入 `"x'; drop table note; --"` 之后表还在，正文被原样存下。

连接的主人要明确。一个请求一个连接或一个会话，用完归还。不要在全局放一个连接然后所有线程共用 sqlite 的默认连接。sqlite 连接对象跨线程使用是受限的。

迁移是有版本的结构变更。应用启动时不应悄悄 `CREATE TABLE` 就算迁移系统。至少要有版本号和只向前的脚本。示例为了短，直接建表。生产要把建表从请求路径拿出去。

SQLAlchemy 2.0 是这套语义的常用映射。新代码用 `select()` 语句，不再写旧的 `session.query` 风格。异步会话是 `AsyncSession`，`async with` 管生命周期：提交、回滚、还连接。懒加载在异步下如果触发了隐式 I/O，会得到 `MissingGreenlet` 一类的错误。关系要在查询里显式加载，不要在序列化时才摸到属性。

连接池的参数是容量，不是装饰：

| 参数 | 作用 |
| --- | --- |
| `pool_size` | 常驻连接数 |
| `max_overflow` | 突发时允许多出来的连接 |
| `pool_recycle` | 在服务端把空闲连接掐掉之前主动换新 |
| `pool_pre_ping` | 取出时先测一下，避免拿到已经死的连接 |

池耗尽的症状是请求堵住。原因常常是会话没有归还，而不是数据库太小。`async with` 或 `try/finally` 必须在异常路径也归还。

ORM 对象不要直接当 HTTP 响应。会话关闭后属性可能访问不到，也会把内部列泄漏出去。在边界转成 D03 的输出对象。

数据库约束是最后一道门。库存不为负可以有 `CHECK`。应用检查和约束都要有：应用给出清楚的错误码，约束挡住绕过应用的写入。

## 会出事的写法

- 用 f-string 拼 SQL。
- 以为 `with connection` 会 `close()`。后面继续用是可以的，但进程退出前要自己关。泄漏的是你以为已经关了却还在事务里。
- 一个事务里做 HTTP 调用。锁和连接被拿着等网络。
- 异步路由里访问未加载的关系属性。在序列化阶段才发 SQL，而且可能直接抛错。

## 示例对照

`examples/part_d/d06_persistence.py` 先在事务里插入再抛 `RuntimeError`，回滚后 `count` 是 0。再插入看起来像注入的字符串，表还在，读回的正文等于原字符串。断言就是参数化和事务的规格。

## 加练

1. 为什么回滚之后连接还能查询？
2. 库存扣减怎样写成一条不会半更新的语句序列？

参考答案：

1. 上下文管理器结束的是事务，不是连接。连接回到自动提交模式或等待下一次事务，仍可执行 `select`。
2. 在一个事务里 `UPDATE ... SET qty = qty - ? WHERE id = ? AND qty >= ?`，看影响行数。0 行就是不够，回滚或返回冲突。不要先 SELECT 再在 Python 里减，再写回，中间会有别的事务插入。

## 面试

### Q1. 参数化为什么是正确性问题？

**考点**：注入。

**回答**：

1. 拼接把数据变成了 SQL 语法。
2. 占位符让驱动按值传递，引号和注释失去语法意义。
3. 表名和列名不能用值占位符。它们必须来自白名单，而不是用户字符串。

### Q2. sqlite 的 `with connection` 提交什么、不提交什么？

**考点**：读过文档的上下文管理器。

**回答**：

1. 无异常则提交，有异常则回滚。
2. 不关闭连接。
3. 所以它适合包住一组写入，不适合当作连接的生命周期。关闭要另写。

### Q3. SQLAlchemy 2 异步会话为什么不能懒加载？

**考点**：隐式 I/O 和显式 `await`。

**回答**：

1. 懒加载会在访问属性时发查询。异步代码里发查询必须 `await`。
2. 隐式触发没有 `await`，驱动会报错或阻塞循环。
3. 查询时写明要加载的关系，会话用 `async with` 保证归还连接。响应使用已经拷贝出来的数据对象。

## 常见错误

- 用 f-string 把用户输入拼进 `WHERE`。
- 捕获异常后不回滚也不抛出，连接留在一个半开的事务里。`with connection` 帮你处理这个范围。
- 认为 SQLite 的 `:memory:` 可以被同进程的另一个连接看见。默认每个连接是自己的内存库。需要共享时要使用指定的共享缓存 URI，那是另一份文档，不是默认行为。

## 练习

1. 去掉示例里的 `raise RuntimeError`，提交后行数应当是多少？
2. 为什么 `except` 之后还要查询 `sqlite_master`？
3. `with connection` 结束时连接关闭了吗？

参考答案：

1. 1。没有异常就会提交那一次插入。
2. 确认参数里的文本没有被当成语句执行，表仍然存在。
3. 没有。它只提交或回滚。关闭要调用 `close()`。

## 小结

事务让一组写入原子化。数据通过占位符进入 SQL，不通过字符串拼接。连接有生命周期，迁移有版本。内存 SQLite 适合把这些语义写成测试。
