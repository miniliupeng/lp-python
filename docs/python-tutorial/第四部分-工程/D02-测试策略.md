# D02　测试策略

> 示例：`examples/part_d/d02_testing_strategy.py`

## 学完你能做什么

把时间、随机和外部系统从逻辑里换掉，让测试在一次函数调用里完成，而不是睡几秒。

## 规格写在输入输出上

`is_expired(created_at, ttl, clock)` 回答“现在是否超过创建时间加生存期”。时钟是参数。示例把时钟停在 `100`，于是 `90 + 5` 已经过期，`99 + 5` 还没有。再把时钟拨到 `104`，后者过期。没有 `sleep`，没有波动。

这就是策略的核心：纯决策函数接收它需要的事实，测试提供事实。副作用留在很薄的边缘，边缘上的测试数量少，决策上的测试数量多。

## 替身要窄

时钟对象只有一个 `time()` 方法。测试传入 `Clock`，生产代码可以传入一个调用 `time.monotonic` 的对象。两边满足同一个小协议，不需要继承同一个基类。B06 的协议思想用在这里。

不要用一个“假数据库”把 SQL 重新实现一遍。那种替身会和真数据库分叉。对数据库，优先用真的 SQLite 内存库测查询语义，D06 就是这样做的。替身适合界面很窄的东西：时钟、随机数种子、一个只记录“有没有被调用”的通知器。

随机数用 `random.Random(seed)` 的实例，不要 `random.seed` 改全局。全局种子会让同进程里的其他测试互相影响。

## 失败信息

断言失败时，左边是实际值，右边是预期值，测试名字说明场景。`assert is_expired(...) is True` 比只写 `assert is_expired(...)` 稍啰嗦，但失败时你知道预期是布尔真，而不是某个真值对象。对布尔结果，显式比较是值得的。

一个测试一种变化。示例如果把“过期”和“未过期”写进同一个函数，是因为它们共享一个固定时钟、都是纯函数，读起来仍是一张表。再复杂就拆开。不要在一个测试里先过期、再修改全局、再启动线程。

## 不要测的东西

- 标准库本身。不要断言 `json.dumps` 的空格风格，除非你的合同真的规定了字节级输出。
- 私有循环变量。
- 日志的整句中文，除非那句文案是用户合同。可以断言级别和“没有把令牌打出来”，D04、E05 会做后者。

覆盖率指出没执行到的行。它不指出缺了哪条规格。`clip` 的上界如果没测，覆盖率可能仍然很高，因为同一行在下界测过了。边界要单独写。

## 机制

测试保护行为：输入和输出、失败的类型、不变量在失败后仍然成立。它不保护你今天选用的私有变量名。

结构上分三层就够用，不必照搬名词：

| 层 | 测什么 | 不测什么 |
| --- | --- | --- |
| 纯函数 | 边界值、错误输入 | 数据库 |
| 模型 | 不变量，例如库存不为负 | SQL 方言 |
| 适配器 | 和真实系统的合同，数量很少 | 全部业务分支 |

替身要窄。一个假时钟只提供“现在”。一个假仓库只记录调用。不要做一个什么都像的假对象，最后测的是假对象自己。

pytest 的价值是失败报告、`pytest.raises`、参数化和 `tmp_path` 这类 fixture。fixture 的 setup 和 teardown 把资源配成对。本分支的示例用标准库 `unittest` 和 `assert`，同样要求每个测试独立。不要依赖测试顺序。

不要 `sleep` 等待条件。注入时钟，或直接调用超时分支。必须等外部端口时，循环检查条件并设置上限，失败信息写出等的是什么。

失败信息要能看出期望和实际。`assert got == expected` 比 `assert condition` 好。自定义断言消息写业务不变量，不写“出错了”。

覆盖率是导航，不是目标。100% 覆盖仍可能漏掉“超额出库”。先写那条测试。

## 会出事的写法

- 测试里连接生产数据库。凭证泄漏，数据被改。
- 用真实 `datetime.now()` 断言等于某一秒。到下一毫秒就失败。
- 捕获异常后 `assert True`。任何异常都能通过，没捕获也没人知道。
- 一个测试函数里测十件事。第一件失败，后面的全没跑。

## 示例对照

`examples/part_d/d02_testing_strategy.py` 展示窄替身：不睡觉、不碰网络，断言失败路径留下的状态。阅读时找“失败之后原状态还在”的那条断言。只有成功路径的测试文件是不完整的。

## 加练

1. 为一个重试函数写测试。时钟怎样注入，才不必 `sleep`？
2. 为什么不断言日志字符串？

参考答案：

1. 传入一个函数 `now`，测试里返回 0、1、2。重试间隔用这个时钟的差值，而不是真的等待。
2. 文案会改。行为是“失败时调用了记录函数，且没有写入密钥”。可以断言记录函数收到的级别和“消息里没有那份密钥”。

## 面试

### Q1. 怎样测一段依赖时间的逻辑？

**考点**：确定性。

**回答**：

1. 把“现在”做成参数，默认才是真时钟。
2. 测试传入假时钟，推进它，断言超时分支发生。
3. `sleep` 又慢又会在负载高时抖动。它不是规格。

### Q2. 替身和真实适配器怎样分工？

**考点**：测试太多会测不到真实系统，太少又慢。

**回答**：

1. 业务规则用替身快速覆盖。
2. 少量合同测试对真实数据库或 HTTP 桩跑迁移和查询。
3. 替身要遵守真实系统的关键语义，例如“唯一键冲突会失败”。否则测试是绿的，生产是坏的。

### Q3. 为什么不测私有方法？

**考点**：重构空间。

**回答**：

1. 私有方法是实现。重构就会改名、内联。
2. 对外行为不变时测试不该失败。
3. 如果一段逻辑很难通过对外行为测到，把它提成纯函数，那就是新的公开单元，而不是去测下划线方法。

## 常见错误

- `time.sleep(0.2)` 然后比较时间戳。调度一忙就抖。
- 测试依赖执行顺序，在模块导入时改全局。
- 为了可测，把所有函数都改成接收十个协作对象。只把真正变化的依赖注进去，其余的直接调用。

## 练习

1. 把生存期改成 0。在时钟等于创建时间时，示例的判断是过期还是不过期？看代码里的比较符。
2. 为什么用 `time.monotonic` 而不是 `time.time` 做生存期？
3. 数据库查询应该用替身还是用内存数据库？

参考答案：

1. `>=`，所以生存期为 0 时，创建时刻当时就算过期。如果规格是“满一整段才过期”，比较符要改，测试先改。
2. `monotonic` 不受系统时间回拨影响，适合量间隔。`time.time` 是墙钟，适合记录“事件发生在几点”。
3. 查询语义用真的 SQLite 内存库。外部网络服务才用窄替身或契约测试。

## 小结

决策函数接收时钟和数据，测试拨动这些输入。替身保持接口窄。断言写规格，不写实现步骤。会抖动的睡眠不是测试策略。
