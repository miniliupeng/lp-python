# D03　边界上的类型与校验

> 示例：`examples/part_d/d03_boundaries.py`

## 学完你能做什么

把“注解”“结构协议”“运行时解析”放在三层里，不再指望其中一层干另外两层的活。

## 三层

1. **注解和类型检查器。** 在开发时看调用是否对得上。它们不随进程部署，除非你另外部署了一个检查步骤。B09 已经说明运行时不自动校验。
2. **`Protocol`。** 描述“有这些方法即可”，用来给检查器看结构类型。`@runtime_checkable` 让 `isinstance` 能做一次很浅的判断：属性在不在。示例里 `Person` 有 `greet`，所以它是 `Greeter`。这个检查不读 `greet` 的参数类型，也不调用它。它挡不住一个 `greet` 方法其实需要两个参数的对象。运行时协议检查是辅助，不是验证器。
3. **边界解析。** 外部来的文本、JSON、环境变量，在进入系统时变成内部类型。失败就拒绝。`parse_port` 只接受 `1` 到 `65535` 的整数。`"http"` 和 `"70000"` 都失败。通过之后，内部函数的参数就是 `int`，不必每个函数再解析一遍字符串。

内部函数信任内部类型。这个信任来自边界只有少数几个，并且都测过。到处 `isinstance` 说明边界没有守住。

## 解析要保留原因

`int(text)` 失败时的 `ValueError` 可以变成你自己的配置错误，用 `raise ... from` 留下数字格式不对这个原因。示例为了短，让 `int` 的异常直接冒出，端口范围则抛出带明确消息的 `ValueError`。生产代码里，配置错误应当指出变量名，例如 `PORT`，而不是只说“invalid”。

不要在解析失败时返回 `None` 再让调用方忘记判断。失败是异常或一个明确的结果类型。如果两种失败都用 `None`，调用方无法区分“没配置”和“配置错了”。

## JSON 和字典

`json.loads` 给出 `dict`、`list`、`str`、`int`、`float`、`bool`、`None`。它不给出你的 dataclass。边界上写一个函数，从字典取出字段、检查类型、构造 `Movement` 或 `Point`。缺字段、类型不对，都在这个函数失败。

3.15 的 `frozendict` 不是 `dict` 的子类。如果边界打算接受它，按 C07 的方式检查 `Mapping`，再仍然构造你自己的内部对象。内部状态不必保留外部的容器类型。

## 机制

三层不要互相替代：

1. 注解和类型检查器在开发时看调用是否对得上。它们不随进程自动执行。
2. `Protocol` 描述结构。`@runtime_checkable` 的 `isinstance` 只看属性在不在。
3. 边界解析把外部的文本、JSON、环境变量变成内部类型。失败就拒绝。

`parse_port` 只接受 1 到 65535 的整数。`"http"` 和 `"70000"` 都失败。通过之后内部函数的参数就是 `int`。

Pydantic v2 是这一层的工业实现，不是语言的一部分。本教程不安装它，示例用标准库把同一条流水线写明白。对照着看，面试才不会只背库的名字：

```text
原始输入
  → 类型强制转换（"20" 可以变成 20，也可以拒绝，策略要明确）
  → 单字段约束（范围、长度、格式）
  → 跨字段约束（结束时间晚于开始时间）
  → 内部对象
```

V2 的核心校验在 `pydantic-core`（Rust）里做，通常比 V1 的纯 Python 快，倍数随模型形状变化，不要背一个固定倍数。对应的 API 要说对：用 `model_validate` 而不是旧的 `parse_obj`，用 `model_dump` 而不是旧的 `.dict()`，用 `field_validator` 和 `model_validator(mode="after")` 而不是旧的 `validator`，ORM 对象用 `from_attributes` 而不是 `orm_mode`。失败是 `ValidationError`，里面是结构化的错误列表，不要只 `str(exc)` 扔给用户。

强制转换是政策。端口可以拒绝 `"080"` 以外的字符串，也可以接受数字字符串。选定之后测试钉死。不要在业务中层再悄悄 `int()`。

JSON 只有七种值。dataclass 要在边界构造。3.15 的 `frozendict` 不是 `dict` 的子类。接受它时检查 `Mapping`，然后仍建成内部对象。

解析失败不要返回 `None`。`None` 分不清“没配置”和“配置错了”。用异常，异常里带字段名。

## 会出事的写法

- 用 `runtime_checkable` 接收 HTTP 正文。方法存在不代表字段合法。
- 捕获所有 `ValueError` 后改用默认端口。错误配置连到了 8000。
- 注解写 `int`，查询参数仍是字符串，视图里直接做算术。
- 把 Pydantic 模型一直传到持久层又传到模板。内部用自己的类型，边界模型停在边界。

## 示例对照

`examples/part_d/d03_boundaries.py` 断言非法端口失败、合法端口得到 `int`、`Protocol` 的 `isinstance` 只要求方法存在。它不导入 pydantic。你应能把示例里的 `parse_port` 讲成上面的流水线：转换、范围、失败类型。

## 加练

1. `"0"` 能不能当端口？看示例的范围，再说一个产品里 0 合法的配置。
2. 跨字段规则“确认密码必须相同”放在哪一层？

参考答案：

1. 示例从 1 开始，`"0"` 失败。超时秒数可以是 0，表示不额外等待。规则跟字段走，不跟“所有数字”走。
2. 两个字段都通过单字段检查之后。用结果对象上的校验，或解析函数的最后一步。不要在数据库里才发现。

## 面试

### Q1. 注解、Protocol、运行时校验各干什么？

**考点**：三层分工。

**回答**：

1. 注解给定类型检查器，运行时默认不执行。
2. Protocol 描述“有这些方法”。运行时检查很浅。
3. 外部输入在边界解析。失败拒绝。内部函数信任内部类型。

### Q2. Pydantic v2 和手写解析怎么选？

**考点**：库解决样板，不改变边界的位置。

**回答**：

1. 字段多、错误要结构化返回给客户端时，用 v2 的模型，核心在 Rust 实现的 pydantic-core。
2. 规则只有一两条时，手写函数更清楚，也没有依赖。
3. 无论哪一种，未校验的字典都不能进库存和转账。API 名字要用 v2：`model_validate`、`model_dump`、`field_validator`。

### Q3. 为什么解析失败不能返回默认值？

**考点**：静默错误配置。

**回答**：

1. 默认端口、默认币种会让系统在错误配置下继续跑。
2. 调用方分不清没填和填错。
3. 启动时失败好过运行一小时后写错账。局部功能的可选配置可以有默认值，但必须是安全的，并且和“解析失败”不是同一条路径。

## 常见错误

- 用 `runtime_checkable` 代替解析。方法存在不代表 JSON 字段合法。
- 在业务中层捕获所有 `ValueError` 再返回默认端口。调用方会在错误配置下悄悄连到 8000。
- 注解写了 `int`，HTTP 查询参数却仍然是字符串，函数里直接做算术。转换发生在视图函数或专门的解析层，不发生在注解里。

## 练习

1. `parse_port("0")` 应当成功吗？看示例的范围。
2. 给 `Person` 增加一个不相关的方法，`isinstance` 结果变不变？
3. 为什么内部的 `Stock.apply` 不再接收字符串形式的数量？

参考答案：

1. 不应当。范围从 1 开始，`0` 抛 `ValueError`。
2. 不变。`runtime_checkable` 只要求 `greet` 存在。
3. 字符串在边界上已经变成正整数和枚举。账本维护的是不变量，不是文本格式。

## 小结

类型检查器看开发期，协议描述结构，解析函数在边界上生产内部对象。`isinstance` 对协议的运行时检查很浅。错误配置要失败，不要变成默认值。
