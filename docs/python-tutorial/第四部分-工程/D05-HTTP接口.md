# D05　HTTP API

> 示例：`examples/part_d/d05_http_api.py`

## 学完你能做什么

用标准库走通一次 HTTP：状态码、路径、JSON 正文。知道一个最小处理器和真正的服务之间还差哪些设计，而不是再套一个框架名词。

## 示例在做什么

`ThreadingHTTPServer` 绑在 `127.0.0.1` 的端口 `0` 上，由操作系统分配空闲端口。线程里 `serve_forever`，主线程用 `urllib.request` 访问 `/health`，期望 200 和 `{"status":"ok"}`。访问 `/missing` 期望 404。最后 `shutdown` 并关闭套接字。

这是教学用的环回请求，不是一个可以暴露到公网的服务器。`http.server` 的文档自己也把它放在开发和测试的位置。生产服务需要进程管理、超时、请求体大小限制、并发模型和一个维护中的框架或服务器。那些不在这一个文件里。

处理器关掉了默认的访问日志，避免示例输出被访问行淹没。生产环境相反，访问日志是有用的，但要走你配置的日志系统，并仍然不记录凭证。

## 接口的形状

即使只有一个健康检查，也可以把以后的规则先说清楚：

- 路径表示资源，`/health` 表示服务自己的健康，不表示业务数据。
- 成功读到了资源用 200，正文是 JSON。没有这个路径用 404。
- 客户端错误用 4xx，服务自己坏了用 5xx。不要用 200 加 `{"ok": false}` 表示失败。调用方会把 HTTP 成功当成业务成功。
- 正文的媒体类型写出来。示例是 `application/json; charset=utf-8`。
- `Content-Length` 和实际字节数一致。示例先把正文编码成 `bytes`，再写长度。

创建资源时用 POST 或 PUT，并说明哪一个是幂等的。PUT 到同一个地址两次，结果应当和一次一样。POST 常常每次都新建，所以不是幂等的。删除应当幂等：删掉一个已经不存在的资源，可以是 204 或 404，选一种写进合同，不要有时 500。

## 分页、超时、大小

列表接口要有上限。一次返回“全部订单”会在数据变多之后把进程打满。用明确的 `limit`，并规定最大允许值。解析查询参数时用 D03 的方式，非法就 400。

客户端要有超时。示例的 `urlopen(..., timeout=2)` 是调用方的超时。服务端也要限制读取请求体的时间，否则一个慢客户端能占住连接。教学服务器没有做完整的超时控制，这是它不能直接上生产的原因之一。

## 和框架的关系

框架负责路由、解析和服务器生命周期。它不替你决定状态码的含义。先把合同写对，再选框架。本教程不安装框架，阅读和运行也不依赖它们。

## 机制

HTTP 合同先于框架。一份最小合同包括：路径、方法、成功状态码、错误状态码、媒体类型、正文大小上限、超时。示例用标准库把 200 和 404 走通，是为了让这些字段可见，不是为了用 `http.server` 上生产。

状态码是给中间件和客户端的。200 表示成功。400 表示请求不合法。401 未认证，403 已认证但无权限。404 没有这个资源。409 冲突。422 常被校验库用来表示正文结构不合法。500 是服务器没有处理好。不要用 200 加 `{"ok": false}`。客户端和网关会把 200 当成功。

幂等：PUT 到同一地址两次，结果和一次一样。DELETE 第二次仍是成功或稳定的 404，选一种写进合同。POST 通常每次新建，不是幂等。重试 POST 要有调用方生成的幂等键。

分页必须有上限。查询参数用 D03 的方式解析，非法是 400。`Content-Length` 按字节算。JSON 用 UTF-8。

框架在这张合同上面做三件事。以 FastAPI 这一支为例，它站在 Starlette 和 Pydantic 上：

1. 路由：路径和方法映射到函数。`APIRouter` 把路由分组。路径参数仍要当不可信文本解析。
2. 依赖注入：`Depends` 把认证、数据库会话做成有向无环图。默认按请求缓存，同一请求里相同依赖只算一次。`yield` 之前获取资源，响应发出后执行 `yield` 后面的清理，路由抛异常也会清理。
3. 生命周期：用 `lifespan` 异步上下文管理器在进程启动时建连接池、在关闭时释放。`on_event("startup")` 已是旧接口，不要写进新代码。

这些名字是为了面试时说得清。本仓库的示例不安装 FastAPI，也不导入它。你要能把 `Depends` 的 `yield` 对应到 B08 的上下文管理器，把 Pydantic 模型对应到 D03 的边界解析。

线程模型：示例的 `ThreadingHTTPServer` 每个请求一个线程，只适合演示。生产要选服务器的工作进程数，CPU 密集不要放在持有请求的线程里空转 GIL。超时在客户端是 `urlopen(..., timeout=2)`，在服务端还要限制读正文的时间和正文大小。示例没有做完整的服务端超时，所以它不能暴露到公网。

健康检查要便宜，不要在里面写数据库。依赖是否可用是就绪检查，失败时编排系统不把流量打过来。

## 会出事的写法

- 把异常字符串放进 500 的 JSON。路径、SQL、密钥泄漏给客户端。
- 健康检查执行写操作。探测把数据改了。
- 没有正文大小上限。一个客户端把内存打满。
- 在依赖的 `yield` 之后才提交事务，却在路由里已经返回了“成功”。清理阶段失败时，客户端以为写进去了。提交点要和合同一致。

## 示例对照

`examples/part_d/d05_http_api.py` 把服务器绑在 `127.0.0.1` 和端口 0 上，操作系统分配空闲端口。线程里 `serve_forever`，主线程请求 `/health` 得到 200 和 `{"status":"ok"}`，`/missing` 得到 404。最后 `shutdown` 并 `server_close`。处理器关掉了默认访问日志，避免测试输出被淹没。生产上访问日志要有，但走日志系统，不记录凭证。

## 加练

1. 为什么端口用 0？
2. 把“创建订单”设计成可重试。状态码和幂等键怎么说？

参考答案：

1. 避免和机器上已有进程冲突。测试才能稳定绑定。
2. 客户端生成幂等键，服务端对同一个键只创建一次。第一次 201，重放返回同一个订单和 200 或仍是 201，合同选一种。不要让重试生成第二张订单。

## 面试

### Q1. 为什么 200 加 `ok: false` 是坏合同？

**考点**：中间件按状态码行动。

**回答**：

1. HTTP 库、网关和监控把 2xx 当成功。
2. 失败会变成成功率 100% 的隐形错误。
3. 客户端错误用 4xx，服务器错误用 5xx。业务拒绝也要有稳定的状态码和错误体，而不是另一套方言。

### Q2. `Depends` 的 `yield` 保证什么？

**考点**：请求级资源的清理。

**回答**：

1. `yield` 前构造依赖，路由函数拿到结果。
2. 响应之后、包括路由抛异常时，执行 `yield` 后面的代码。
3. 同一请求内默认缓存这个依赖，所以多个依赖共享同一个数据库会话。这不是全局单例。下一个请求要新的会话。

### Q3. 应用启动和关闭放哪里？

**考点**：lifespan，而不是导入期副作用。

**回答**：

1. 放在 `lifespan` 里：进入时创建连接池，退出时关闭。
2. 不要在 import 时连接。测试导入模块不应连生产。
3. 关闭要有期限。D09 讲 SIGTERM 时把已接收的工作做完，不再接新的。

## 常见错误

- 健康检查去连一次生产数据库并执行写操作。健康检查应当便宜。要检查依赖，单独做一个就绪检查，并说明失败时编排系统会怎样做。
- 把异常字符串放进 500 的 JSON。那是内部信息。
- 在处理器里做 CPU 密集计算。默认的线程服务器每请求一线程，受 GIL 和线程数量限制。先把合同做对，再按 C05 的模型选执行方式。

## 练习

1. 示例为什么把端口设成 0？
2. `/health` 的正文是字节还是字符串？长度按哪个算？
3. 为什么 200 加 `ok: false` 是个坏合同？

参考答案：

1. 让操作系统分配空闲端口，避免和机器上已有服务冲突，测试才能稳定绑定。
2. 网上传送的是字节。示例的正文是 UTF-8 字节，`Content-Length` 是字节数，不是字符数。
3. HTTP 库和中间件会把 200 当成功。失败应当是 4xx 或 5xx，调用方不用再懂你的私有 JSON 方言才能发现错误。

## 小结

一个 API 合同包括路径、方法、状态码、媒体类型和错误形状。标准库足够演示环回上的 200 和 404。生产环境还需要超时、限制、日志和进程管理，这些不因为换了框架就自动出现。
