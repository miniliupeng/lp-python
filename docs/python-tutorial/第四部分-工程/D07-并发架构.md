# D07　并发架构

> 示例：`examples/part_d/d07_concurrency_architecture.py`

## 学完你能做什么

用有界队列表达背压，用哨兵停止消费者，并把超时和取消说成结构设计而不是事后补的 `sleep`。

## 队列划分主人

多个线程一起改 `Stock` 的字典，不变量会坏。更稳的结构是：只有一个工作者执行 `apply`，其他人把 `Movement` 放进队列。数据的主人只有一个。C05 的锁适合保护很短的计数；一长串业务规则更适合串行化到一个主人那里。

`queue.Queue` 是线程安全的移交点。示例先证明 `maxsize=1` 时，第二次 `put_nowait` 抛 `queue.Full`。这就是背压：生产者看到拒绝，而不是无限堆积把内存吃完。阻塞的 `put` 则会让生产者等。两种都是策略。无限队列不是背压，是把问题推迟到内存耗尽。

网络服务里的背压要能传到客户端：拒绝新任务、返回 429 或让调用方重试。只在内部堵住、外面还继续接收，连接一样会堆满。

## 停止

示例用一个专用的 `STOP` 对象当哨兵。消费者看到它就退出。不要用 `None` 当哨兵，除非队列里的合法数据永远不可能是 `None`。专用对象用 `is` 判断，不会和整数任务混淆。

工作者在 `finally` 里 `task_done`。如果有人在 `join` 队列，漏掉 `task_done` 会永远等下去。示例没有 `join` 队列，而是 `join` 线程。两条路都可以，不要混用到计数对不上。

主线程必须 `join` 工作者。守护线程会在进程退出时被切断，队列里的最后一项可能没处理完。

## 超时

任何等待都要有上限：`queue.get(timeout=...)`、HTTP 客户端的 timeout、锁的获取。没有上限的等待会变成“服务还活着但不再前进”。超时之后的失败要可见，记日志并返回错误，不要空转重试。

重试只对可能短暂失败的操作有意义，并且要有次数上限和间隔。间隔不要所有客户端同一秒醒来。幂等的操作才可以安全重试：扣库存如果没有幂等键，重试会扣两次。幂等键是调用方给的唯一编号，服务端记下“这个编号已经做过”，再来就返回上次的结果。

## 取消

协程的取消是 C06 的 `CancelledError`。线程没有同等可靠的强制取消。线程的取消通常是设一个事件，让它在下一次循环自己退出。不要 `Thread._stop` 之类的私有手段。进程可以用进程组的信号，D09 只演示应用自己的关闭标志，不在示例里向自己发信号。

## 机制

并发架构先回答三个问题：谁有权改这份数据，排队时满了怎么办，停止时正在做的工作怎么办。

队列划分主人。一份可变状态只由一个协程或一个线程修改，其他人通过队列提交命令。这样不变量留在一个地方。`queue.Queue(maxsize=n)` 在满时阻塞生产者，这是背压。没有上限的队列会在消费者变慢时吃光内存。

停止要有标志。生产者不再放入，消费者取出剩余项，然后退出。主线程 `join`。守护线程做不到把队列排空。

超时是合同的一部分。拿锁、等队列、等下游都要有期限。到期是失败，不是再等一会儿。失败要可见：返回给调用方，或记入失败队列。不要在超时后假定写入已经成功。

取消是 asyncio 的停止方式。取消必须传播，清理放在 `finally`。线程没有同样的取消语义。线程只能看标志，在安全点自己退出。强行杀线程不是 Python 的支持路径。

进程之间用消息，不共享内存里的列表。需要共享时用进程安全的队列，并接受序列化成本。

背压的位置：队列满、信号量满、数据库池满，都是同一种拒绝。信号量限制同时进行的下游调用数。没有它，一个慢下游会让所有任务堆在内存里。3.11 的 `asyncio.Semaphore` 和线程的 `Semaphore` 一样，只是等待方式不同。不要在异步代码里用阻塞的线程信号量。

## 会出事的写法

- 无界队列加无界重试。下游一停，进程内存上涨。
- 超时后重试，旧请求其实还在执行。两笔一起写。重试要有幂等键，或者确认旧的已经取消。
- 停止信号只设了标志，谁也不检查。进程要等自然结束。
- 在持有数据库事务时等待队列。锁的范围穿过了网络等待。

## 示例对照

`examples/part_d/d07_concurrency_architecture.py` 用有上限的队列或信号量证明：生产者会被背压挡住，停止之后已放入的工作仍被处理完，而不是丢掉。断言看处理计数和剩余队列，不看睡眠时间。

## 加练

1. `maxsize=1` 的队列，消费者停住时，第二次 `put` 会怎样？测试如何避免真的卡住？
2. 为什么取消协程之后不能假设“写入没有发生”？

参考答案：

1. 不带超时的 `put` 会阻塞。测试用 `put_nowait` 断言 `queue.Full`，或者用很短的 `timeout` 断言 `queue.Full`。不要 `sleep` 赌它堵住了。
2. 取消发生在 `await` 点。`await` 之前的写入可能已经提交。清理和幂等要承认“可能写过”。

## 面试

### Q1. 背压是什么？没有它会怎样？

**考点**：队列和内存。

**回答**：

1. 消费者慢时，生产者必须减速或被拒绝。
2. 无界队列把压力藏成内存上涨，最后进程被杀死，工作全部丢失。
3. 有界队列、信号量、有限连接池都是背压。拒绝时要有明确的错误，调用方才能重试或降级。

### Q2. 优雅停止和杀进程的差别？

**考点**：已接收工作。

**回答**：

1. 停止接受新工作，等待已接收的工作完成或到达期限，然后释放连接。
2. 直接杀进程会打断事务和半截写入。
3. 期限到了仍未完成的工作必须可见，不能假装成功。D09 把信号和健康检查接上。

### Q3. 为什么一份数据最好只有一个写者？

**考点**：锁的范围。

**回答**：

1. 多个写者要锁住每一个不变量，顺序错了就死锁。
2. 单写者把命令排成队列，状态机在一个地方转移。
3. 读可以复制快照。读要强一致时仍要和写者同步，不能假设队列延迟是 0。

## 常见错误

- 无界队列加上比消费者更快的生产者。
- 多个工作者不持锁地改同一份账，还以为队列已经让他们安全。队列保证的是移交，不是“出队之后可以随便共享可变对象”。出队后的对象如果只有这个工作者使用，才是安全的。
- 超时后立刻无间隔重试，把下游打得更满。

## 练习

1. `maxsize=1` 且已经有一项时，`put_nowait` 发生什么？
2. 为什么哨兵是 `object()` 而不是 `0`？
3. 重试扣款之前，调用方必须提供什么？

参考答案：

1. 抛 `queue.Full`。队列不会为了这次放入而扩容。
2. `0` 可能是合法任务。新创建的 `object()` 只和自己 `is` 为真。
3. 幂等键，或者服务端能识别“同一请求”的其他稳定标识。否则重试会重复扣款。

## 小结

用队列把共享可变状态收成一个主人。队列要有上限，停止要用专用哨兵，等待要有超时。重试必须有上限，并且只作用在幂等操作上。
