# D01　项目布局与依赖

> 示例：`examples/part_d/d01_project_layout.py`

## 学完你能做什么

分清源码、项目元数据和锁文件。这个分支本身只有三样东西：根 `README.md`、`docs/python-tutorial/` 正文、`examples/` 示例。示例断言这三样都在，并且不去读取一份并不存在的工程配置。

教程示例只依赖标准库。下面用一段写在示例里的 TOML 说明 `pyproject.toml` 长什么样，而不是要求本教程目录本身变成一个可安装的第三方包。

## `pyproject.toml` 声明什么

示例读出的是一段内嵌声明，不是仓库根目录上的文件：

- `project.name` 是 `python-tutorial`。
- `requires-python` 是 `>=3.12`。
- `dependencies` 是空列表。示例不安装第三方包。

这是给安装工具和人的合同长什么样：项目不承诺能在 3.11 上跑。它不证明每一行代码都用到了 3.12 的新语法。本教程的示例确实停在 3.12 能执行的语法上，更高版本的语法只写在 C07 的说明里。真要发布一个库时，把同样的表写进 `pyproject.toml`，再用锁文件记下解析结果。本教程目录不附带那两份文件。

依赖列表写的是允许的版本范围，不是某一次安装的完整闭包。锁文件记录解析结果：每个包的具体版本和哈希。可重复安装靠锁文件，不靠“半年前我机器上正好是这个版本”的记忆。

不要手改锁文件来“升级一个包”。用项目选定的工具重新解析，然后把锁文件和代码一起审查。本教程不改这两份文件。

## 源码布局

一个可安装的包通常放在 `src/包名/` 或仓库里的一个导入包目录。测试放在包外，避免测试目录被当成产品代码安装进去。教程的 `examples/` 是脚本，不是一个要安装的包。它们用 `Path(__file__).resolve().parents[2]` 找到仓库根，而不是依赖你从哪个目录启动。

`sys.path` 的第一项通常是脚本所在目录或空字符串（当前目录）。这就是为什么在错误的目录里启动，导入会找到另一个同名文件。应用程序应当装进虚拟环境，用明确的入口点启动，而不是要求用户 `cd` 到某个文件夹再 `python 某个文件`。教程为了零依赖，仍然提供直接运行脚本的方式。

## 虚拟环境

虚拟环境里有独立的 `python` 和 `site-packages`。系统解释器留给系统包管理器。混装会让“这台机器能跑”无法迁移。

环境变量 `VIRTUAL_ENV` 和提示符能告诉你现在在不在环境里。更可靠的是看 `sys.prefix` 是不是指向项目的环境目录。教程不要求你为了示例去创建环境。

## 配置不要写进代码

数据库地址、密钥、端口放在环境或部署系统里。仓库里提交的是示例配置的字段名，不是生产密钥。D04 把这件事做成读取函数。这里先定规则：能让同一个人在笔记本和生产用同一份源码启动，靠的是配置不同，不是改代码。

## 机制

一个可安装的 Python 项目用 `pyproject.toml` 声明自己。PEP 621 的 `[project]` 表包括名字、版本、`requires-python`、依赖列表。构建后端写在 `[build-system]`。声明回答“这个项目是什么、能在什么解释器上装、需要哪些依赖范围”。它不负责把依赖真的装进机器。

锁文件回答另一次问题：这次解析得到了哪些精确版本和哈希。应用提交锁，构建才可重复。库通常只提交范围，让使用它的应用去锁。`requires-python = ">=3.12"` 不会在你直接运行源码时阻止 3.11，安装器才会看它。不要写成某一个补丁号，除非你在绕开一个具体的解释器缺陷。

虚拟环境是独立的 `site-packages`。系统解释器留给操作系统包。`venv` 是标准库，`uv` 是现在常见的安装器和解析器，能创建环境、锁依赖、同步锁定结果。本教程的空分支不带 `uv.lock`，示例也不调用 `uv`。示例只断言：根上有 `README.md`，教程索引在 `docs/python-tutorial/README.md`，`examples/run_all.py` 存在，并且一段样本 TOML 的名字和 `requires-python` 符合预期。`tomllib.loads` 吃字符串。`tomllib.load` 才吃二进制文件。

源码布局常见两种：src 布局把包放在 `src/包名`，避免测试意外导入到仓库里未安装的半成品；扁平布局把包放在仓库根。小脚本可以没有包。无论哪一种，可执行入口不要在导入时连数据库。

配置不写进代码。环境变量或仓库外的配置文件提供端口、路径和密钥。默认值只能是开发安全的值，不能是生产口令。

## 会出事的写法

- 把 `pip install` 装进系统 Python，和发行版的包混在一起。下一个系统升级把依赖弄乱。
- 提交了声明却不锁应用依赖。今天能装，下周解析到不兼容的新版本。
- `loads(path.read_bytes())`。`loads` 要 `str`。
- 仓库里放 `.env` 且里面有生产密钥。`.env` 只作本地样例，真实密钥在环境里。

## 示例对照

`examples/part_d/d01_project_layout.py` 从 `examples/part_d/` 往上两级找到仓库根，检查三份入口文件，并用 `tomllib.loads` 解析样本。样本里的依赖列表是空的，因为教程示例不依赖第三方包。这不是说生产服务不该有依赖。

## 加练

1. 为什么教程示例可以没有虚拟环境，服务却应该有？
2. `requires-python` 和锁文件各阻止哪一类事故？

参考答案：

1. 示例只用标准库，解释器本身就够。服务有第三方依赖，不隔离就会污染系统解释器，也不能在两台机器上得到同一套版本。
2. `requires-python` 阻止安装器把包装进太旧的解释器。锁文件阻止“范围内但你没测过的新版本”进入这次构建。

## 面试

### Q1. `pyproject.toml`、虚拟环境、锁文件各是什么？

**考点**：三件东西经常被说成“依赖管理”。

**回答**：

1. `pyproject.toml` 是声明：名字、Python 版本范围、依赖范围、构建后端。
2. 虚拟环境是安装位置，避免写进系统解释器。
3. 锁文件是一次解析的精确结果。应用提交它。库把范围留给应用去锁。

### Q2. 为什么不把依赖装进系统 Python？

**考点**：隔离。

**回答**：

1. 操作系统和其他工具可能依赖另一套版本。
2. 升级系统包会改掉你的服务依赖。
3. 每个项目一个环境，删除环境就等于卸载这个项目的依赖。解释器本身仍用 3.12 以上的发行版。

### Q3. src 布局解决什么？

**考点**：导入路径。

**回答**：

1. 仓库根经常在 `sys.path` 里。扁平布局下，测试可能导入到源码树而不是已安装的包。
2. src 布局让未安装时导不到包，迫使测试走安装结果。
3. 小教程脚本不必上 src 布局。有包、有测试、要发布时再上。

## 常见错误

- 把 `requirements.txt` 的一次 `pip freeze` 当成设计文档。冻结结果没有区分直接依赖和传递依赖。现代项目用 `pyproject.toml` 写直接依赖，用锁文件写闭包。
- 为了让脚本能导入，在每个文件里修改 `sys.path`。安装包或使用 `-m`。
- 把教程仓库和将要发布的库混成同一个目录义务。教学脚本可以只靠标准库运行；库再单独声明依赖。

## 练习

1. 不看示例，写出仓库根目录相对 `examples/part_d/d01_project_layout.py` 要向上几级。
2. `requires-python` 和锁文件各回答哪个问题？
3. 为什么教程示例不 `import fastapi`？

参考答案：

1. 文件在 `examples/part_d/`，向上两级是仓库根。`parents[0]` 是 `part_d`，`parents[1]` 是 `examples`，`parents[2]` 是根。
2. `requires-python` 回答语言版本下限。锁文件回答这一次解析出的依赖闭包。
3. 教程的可执行规格只使用标准库，避免把“读懂 Python”绑在一次环境同步上。框架留到合同写清楚之后再选。

## 小结

项目元数据、锁文件和源码各管一件事。本教程把声明写在示例字符串里，避免假装已经发布了一个包。路径用 `__file__` 解析，配置不写死在代码里。
