# D04　日志、配置与错误

> 示例：`examples/part_d/d04_logging_config.py`

## 学完你能做什么

用日志而不是 `print` 记录运行事实，在写日志时去掉固定的敏感片段，并让配置来自调用方传入的环境映射。

## 日志有级别和去向

`logging` 把事件交给 handler。示例用一个 `StringIO` 当去向，方便断言，生产环境里去向是标准错误、文件或采集代理。级别用来过滤：`INFO` 以上才输出时，`DEBUG` 不会出现。格式字符串决定每一行长什么样。

示例的业务代码写 `logger.info("ready")`，不关心这句话最后进了哪个文件。这就是和 `print` 的差别。`print` 没有级别，测试也难以把“给用户的输出”和“给运维的诊断”分开。

库代码使用 `logging.getLogger(__name__)`，不要在库里调用 `basicConfig`。`basicConfig` 是应用程序入口的事，调用一次决定默认格式。库如果自己配置根日志，会覆盖宿主的决定。

示例把 `propagate` 设为假，避免这条记录再冒泡到根日志、在测试输出里重复出现。应用程序里是否冒泡，取决于你想不想让根 handler 统一收集。

## 不要记录秘密

示例故意写了一条 `token=secret`，过滤器把子串 `secret` 换成 `***`，断言最终文本是 `token=***`。这只是一层保险，而且很浅：它只认这一个子串。真正的规则是 **不要把令牌、密码、身份证号放进日志消息**。过滤器用在你无法完全控制的第三方消息上，不能代替“根本不记录”。

格式化时也不要把秘密当参数传进去。`logger.info("token=%s", token)` 同样会进文件。参数化日志是为了避免拼接和重复格式化，不是为了安全。

## 配置

进程的配置来自环境，这是十二因子应用的做法：同一份代码，不同的环境变量。读取时集中在一个函数里，给出类型正确的值或立刻失败。不要在业务深处 `os.environ["PORT"]`，那样缺配置的位置散落各处，测试还得改真正的环境变量。

测试传入一个普通字典当环境。D03 的 `parse_port` 就是解析器。把字典和解析器合在一起，入口函数大约是：读 `PORT`，没有则用默认值，有则解析。默认值只属于本地开发。生产环境缺少必填项时应当拒绝启动，而不是悄悄用默认数据库。

## 错误对象

用户能看到的错误和日志里的错误不是同一份文本。给用户的是他们能行动的句子：“端口配置不合法”。给日志的是类型、变量名、请求号，仍然不含秘密。不要把 Python 回溯原样返回给 HTTP 客户端。回溯留在服务器日志里。

异常用来表达控制流里的失败。日志用来留下已经发生的事实。捕获异常、记一条日志、再原样抛出，是边界上的做法。捕获后既不记录也不抛出，失败就消失了。

## 机制

日志是给运行中的进程看的结构化事件，不是 `print`。`logging` 有级别：DEBUG、INFO、WARNING、ERROR、CRITICAL。级别决定什么被发出去。处理器决定去向：stderr、文件、采集系统。格式器决定每条长什么样。

业务代码拿 `logger = logging.getLogger(__name__)`。不要在库里调用 `basicConfig`。应用入口配置一次。库只产生记录。

不要记录密钥、口令、会话令牌、完整卡号。用户标识可以用不可逆的短哈希或内部 id。异常可以记录类型和你自己的错误码。原始 SQL 和用户正文不要整段进日志。

配置来自环境。12-factor 的做法是：代码里没有环境差别，进程环境提供端口、数据库地址、日志级别。缺必填项就启动失败。示例可以读 `os.environ` 的副本，测试传入字典，不改真正的环境，或者改了一定复原。

错误对象是给调用方的。日志是给运维的。两者不要混成一个字符串。对用户说“请求无效”，日志里写内部原因。不要把 `str(exc)` 直接返回给 HTTP 客户端，那会泄漏路径和 SQL。

`raise ... from` 保留原因链，日志打印异常时用 `logger.exception` 或 `exc_info=True`，才会有回溯。`logger.error("失败")` 没有回溯，事后无法定位。

## 会出事的写法

- `print` 调试留在请求路径上。无法按级别关闭，也无法带上请求号。
- 日志格式里 `%s` 写成 f-string 先拼好。级别不够时字符串已经拼了，而且还可能把大对象转成文本。用 `logger.info("listen %s", port)` 的参数形式。
- 每个模块 `basicConfig`。重复处理器，一条日志打两遍。
- 把环境变量读进全局之后在测试里改 `os.environ` 不恢复。后面的测试看见脏配置。

## 示例对照

`examples/part_d/d04_logging_config.py` 应断言：缺少必填配置会失败，日志记录里没有传入的假密钥，级别过滤后 DEBUG 不会出现在指定处理器里。用 `assertLogs` 或一个列表处理器收集记录，不要看 stdout 的打印。

## 加练

1. 写一条“连接失败”的日志调用，要求不拼接字符串，并且能留下异常回溯。
2. 配置字典里端口非法时，应该在哪失败？

参考答案：

1. `logger.exception("连接失败 host=%s", host)`，放在 `except` 里。不要把口令放进 `%s`。
2. 在进程启动、绑定套接字之前。解析函数抛异常，进程以非零退出。不要先听 0 端口再发现配置错了。

## 面试

### Q1. 为什么不直接 `print`？

**考点**：级别、去向、结构。

**回答**：

1. `print` 没有级别，生产上关不掉调试。
2. 日志可以同时给 stderr 和采集器，并带上 logger 名字。
3. 参数化消息避免无谓的字符串构造，也避免把秘密拼进一条无法过滤的文本。

### Q2. 异常和日志怎么分工？

**考点**：控制流和观测。

**回答**：

1. 异常告诉调用方失败了，以及要不要处理。
2. 日志告诉运维发生了什么。边界记一次即可，不要每一层都记同一条。
3. 对用户的消息和日志里的细节分开。用户不看 SQL，日志不看口令。

### Q3. 配置放哪里？

**考点**：12-factor 和启动失败。

**回答**：

1. 环境变量或仓库外的配置，不写进代码。
2. 必填项缺失或非法，进程启动失败。
3. 测试注入字典或临时环境，不依赖开发者笔记本上的全局变量。

## 常见错误

- 用根日志器在每个模块里 `basicConfig`。
- 把 `logger.exception` 用在没有异常的地方。它读取当前异常信息。没有异常时用 `error` 或 `info`。
- 配置函数在缺失时返回空字符串，调用方再去连接 `""`。缺失应当在启动时失败。

## 练习

1. 过滤器如果写成“消息里出现 `secret` 就整条丢弃”（返回 `False`），和示例的替换策略有什么不同？
2. 为什么库里不调用 `basicConfig`？
3. 测试怎样避免修改真实的 `os.environ`？

参考答案：

1. 返回 `False` 会让这条记录消失，连“曾经试图记录令牌”这个事实都没有。示例保留事件，只换掉固定子串。更好的做法是从一开始就不记录令牌。
2. 那是应用入口的全局决定。库配置根日志会干扰宿主。
3. 让读取函数接收字典，测试传入字典。不在测试里改进程的真实环境。

## 小结

日志是带级别的事件，去向由 handler 决定。秘密不要进入消息。配置集中解析，缺必填项就启动失败。用户可见的错误和服务器上的回溯分开。
