# B08　上下文管理器

> 示例：`examples/part_b/b08_context.py`

## 学完你能做什么

用 `with` 表达“进入时取得，离开时一定释放”，包括块里发生了异常的情况。

## 协议

`with obj` 调用 `obj.__enter__()`，把返回值绑到 `as` 后面的名字。离开块时，无论正常结束还是有异常，都调用 `__exit__(exc_type, exc, traceback)`。没有异常时这三个参数是 `None`。

`__exit__` 返回真值表示 **抑制** 这个异常，异常不会继续传播。返回假值或 `None` 表示不抑制。示例的 `Resource` 返回 `False`，所以 `RuntimeError` 仍然冒出来，但 `closed` 已经是 `True`。

不要为了“看起来处理过了”返回 `True`。抑制异常等于告诉调用方这块成功了。只有当你真的处理了这个异常、调用方不应该再看到它时才返回真值。文件对象的 `__exit__` 不会吞掉你的 `ValueError`。

## `contextmanager`

生成器加 `@contextmanager` 可以少写一个类。`yield` 之前是进入，`yield` 的值是 `as` 得到的对象，`yield` 之后是退出。退出代码放在 `finally` 里，这样有异常时也会执行。

```python
@contextmanager
def opened():
    state = {"open": True}
    try:
        yield state
    finally:
        state["open"] = False
```

`yield` 只能有一次。生成器在 `yield` 之后又产出，`contextmanager` 会报错。需要记住很多状态时，类比生成器清楚。

`contextlib` 里还有 `closing`、`suppress`、`nullcontext`。`suppress(FileNotFoundError)` 只吃掉你点名的异常。它比自己写一个返回 `True` 的 `__exit__` 更不容易扩大范围。

## 多个资源

可以写多行 `with`，或者在 3.10 及以后把多个上下文管理器放在括号里换行。后进入的先退出，和嵌套 `with` 一样。不要为了少缩进就把两个不相关的资源硬塞进一个生成器。

## 和异常章节的关系

`with` 就是把 `try` / `finally` 收成一个对象。A10 说过 `finally` 里不要 `return`。同样，`__exit__` 或 `contextmanager` 的 `finally` 里也不要 `return` 去替换原来的异常。释放资源，然后让原来的异常继续走。

## 机制

`with` 调用 `__enter__`，把返回值绑到 `as` 后面的名字。离开块时调用 `__exit__(exc_type, exc, tb)`。没有异常时三个参数是 `None`。`__exit__` 返回真值会吞掉异常。返回假或 `None` 则异常继续传播。吞掉异常必须是有意的，例如“忽略文件已不存在”。不要用返回 `True` 来当 `except Exception`。

`contextlib.contextmanager` 把生成器变成上下文管理器。`yield` 之前是进入，`yield` 的值给 `as`，`yield` 之后是退出。`yield` 必须在 `try/finally` 里，否则进入之后、退出代码之前的异常会跳过清理。标准库的装饰器已经把生成器包成正确的结构，但你写的 `try` 仍然要包住需要清理的部分。

多个资源用嵌套 `with` 或一个 `with` 里逗号分隔。先进入的后退出。不要先手动 `open` 再放进 `with`，中间如果抛异常，文件还没进上下文。

`contextlib.ExitStack` 适合数量到运行时才知道的资源。它把多个上下文登记起来，离开时按相反顺序关闭。

`contextlib.suppress(FileNotFoundError)` 是有意吞掉某一种异常的写法，比 `__exit__` 返回 `True` 更清楚。

锁、事务、小数上下文、临时改目录，都是这个协议。sqlite 连接的 `with` 提交或回滚，但不关闭连接。那是库的选择，不是协议的缺陷。D06 会再强调。

## 会出事的写法

- `__exit__` 一律 `return True`。所有异常消失。
- 生成器在 `yield` 之后才 `close()`，并且 `yield` 不在 `finally` 保护范围内。异常路径泄漏资源。
- 在 `__enter__` 里获取了锁，`__exit__` 的某些分支忘记释放。用 `try/finally` 包住释放。
- 用上下文管理器隐藏重试。重试是另一种控制流，混进 `__exit__` 会让块执行两次，读者看不见。

## 加练

1. 写一个计时上下文，退出时把耗时记到列表里。异常时也要记。
2. `__exit__` 返回 `True` 和 `suppress` 有什么使用上的差别？

参考答案：

1. `yield` 前记 `perf_counter`，`try/finally` 里 `yield`，`finally` 里再记一次并 append 差值。异常会在 `finally` 之后继续抛。
2. 返回 `True` 吞掉一切传到 `__exit__` 的异常。`suppress` 只吞列出的类型。生产代码用后者，或者在 `__exit__` 里比较 `exc_type`。

## 面试

### Q1. `__exit__` 怎样抑制异常？

**考点**：返回值的含义。

**回答**：

1. 返回真值表示已处理，异常不继续传播。
2. 返回假或 `None` 表示不处理。
3. 抑制必须针对具体类型，并记日志。默认不要抑制。

### Q2. `with` 和 `try/finally` 的关系？

**考点**：协议是语法糖，也是约定。

**回答**：

1. `with` 保证 `__exit__` 被调用，相当于把清理放进 `finally`。
2. 它还能把资源对象交给块内名字，并允许多个资源按顺序进入、反序退出。
3. 清理逻辑写在资源自己的类里，调用方不会每个地方复制一遍 `close`。

### Q3. 为什么 sqlite 的 `with connection` 不等于关闭连接？

**考点**：读文档里的协议实现，而不是望文生义。

**回答**：

1. 这个上下文管理器在成功时提交，在异常时回滚。
2. 它不调用 `close()`。连接还要单独关，或者用会关闭的封装。
3. 示例在 D06：块里抛异常后插入被回滚，连接仍可继续查询。

## 常见错误

- `__enter__` 返回 `self`，调用方却以为 `as` 拿到了另一种对象。返回什么就在文档里写什么。锁的 `__enter__` 常常返回自己，文件的 `__enter__` 也返回自己。
- 在 `__exit__` 里做可能失败的第二次清理，又不处理。清理代码自己抛异常时，原来的异常会变成上下文。能简单就不要再添失败点。
- 自己调用 `__enter__` 而不调用 `__exit__`。用 `with`。

## 练习

1. 写一个上下文管理器，进入时把列表清空的动作推迟到退出时完成。退出后列表应为空。用类或 `contextmanager` 都可以。
2. 块里抛了 `RuntimeError`，怎样让它继续传播？
3. 什么时候选类，什么时候选 `contextmanager`？

参考答案：

1. `yield` 之后 `items.clear()`，并且写在 `finally` 里。
2. `__exit__` 返回 `False` 或 `None`。生成器版本不要在 `finally` 里吞掉异常。
3. 状态只是“进来、出去”两段时用 `contextmanager`。要给调用方一堆方法，或者生命周期里有多个字段时用类。

## 小结

`with` 保证 `__exit__` 被调用。返回真值才会吃掉异常，默认不要吃。`contextmanager` 用一次 `yield` 把进入和退出分开，清理放在 `finally`。
