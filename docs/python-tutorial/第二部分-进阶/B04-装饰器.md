# B04　装饰器

> 示例：`examples/part_b/b04_decorators.py`

## 学完你能做什么

把“调用前后多做一点事”写成可复用的函数，保留原函数的名字和文档，并说对装饰器叠放的顺序。

## 装饰器是函数

`@counted` 写在 `def inc` 上面，等价于：

```python
def inc(number: int) -> int:
    return number + 1

inc = counted(inc)
```

`counted` 接收原函数，返回一个新函数。之后名字 `inc` 指向新函数。这就是全部机制。没有另一套“装饰器字节码”。

示例里的包装函数在调用前把 `calls` 加一。`calls` 放在包装函数这个对象上，而不是放在默认参数里。每次调用同一个 `inc`，计数会累加；这是有意共享的状态，和 B01 那个意外共享的默认列表不是一回事。你要能指出状态放在哪。

## `functools.wraps`

不用 `wraps` 时，包装函数的 `__name__` 和 `__doc__` 是 `wrapper` 自己的。栈回溯、帮助文本和一些注册系统会显示错名字。`@functools.wraps(fn)` 把原函数的这些属性复制过来。

示例断言 `inc.__name__ == "inc"`，文档字符串里仍有“加一”。写装饰器时默认加上 `wraps`，除非你故意要一个全新的函数对象并且不关心元数据。

`wraps` 还会更新 `__wrapped__`，指向被包住的函数。调试时可以沿这条链找到原函数。它不会自动让签名检查变魔术，类型检查器对装饰器仍然比较严格。

## 带参数的装饰器

`tag("outer")` 不是装饰器，它是 **制造装饰器的函数**。调用之后才得到真正的装饰器，那个装饰器再接收函数。所以结构是三层：参数、被装饰的函数、实际的包装。

少一层是最常见的笔误：写成了 `def tag(fn)` 却用 `@tag("outer")` 去调用。层数要和 `@` 后面的调用次数一致。

## 叠加顺序

```python
@tag("outer")
@tag("inner")
def value() -> int:
    return 1
```

等价于 `value = tag("outer")(tag("inner")(value))`。离函数最近的装饰器先包。调用时最外层先进入。示例的结果是 `("outer", ("inner", 1))`。

读这种代码时从下往上看“谁先包住原函数”，从上往下看“调用时谁先执行”。两个方向不要混成一句口诀。

## 类也可以当装饰器

实现了 `__call__` 的类，实例可以当装饰器返回的包装物。需要保存多份状态时，类比往函数上挂属性清楚。本教程的示例用函数，是因为状态只有一个计数。不要为了“更面向对象”把三行闭包扩成一个类。

## 常见错误

- 包装函数忘记 `return fn(*args, **kwargs)`，被装饰的函数变成总是返回 `None`。
- 忘记 `wraps`，测试框架按名字找测试时找不到。
- 装饰器在导入时执行。不要在装饰器里连接网络。注册到一个列表里是可以的，那是定义期想要的副作用。

## 练习

1. 写一个装饰器 `double_result`，把原函数的返回值乘 2。假设返回值是数字。
2. 两个这样的装饰器叠在一起，`lambda: 3` 的结果是多少？先预测再跑。
3. `wraps` 复制了什么，没有自动做什么？

参考答案：

1. 包装函数 `return fn(*args, **kwargs) * 2`，并用 `wraps`。
2. 先包的那一层先乘，后包的再乘，结果是 `12`。两层都是乘 2。
3. 它复制名字、文档、注解等元数据，并设置 `__wrapped__`。它不会把类型注解变成运行时校验。

## 小结

`@decorator` 就是调用装饰器再把名字绑到返回值上。用 `wraps` 保留原函数的身份。带参数就多一层工厂函数。离 `def` 最近的装饰器最先包住原函数。
