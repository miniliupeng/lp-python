# B04　装饰器

> 示例：`examples/part_b/b04_decorators.py`

## 学完你能做什么

把“调用前后多做一点事”写成可复用的函数，保留原函数的名字和文档，并说对装饰器叠放的顺序。

## 装饰器是函数

`@counted` 写在 `def inc` 上面，等价于：

```python
def inc(number: int) -> int:
    return number + 1

inc = counted(inc)
```

`counted` 接收原函数，返回一个新函数。之后名字 `inc` 指向新函数。这就是全部机制。没有另一套“装饰器字节码”。

示例里的包装函数在调用前把 `calls` 加一。`calls` 放在包装函数这个对象上，而不是放在默认参数里。每次调用同一个 `inc`，计数会累加；这是有意共享的状态，和 B01 那个意外共享的默认列表不是一回事。你要能指出状态放在哪。

## `functools.wraps`

不用 `wraps` 时，包装函数的 `__name__` 和 `__doc__` 是 `wrapper` 自己的。栈回溯、帮助文本和一些注册系统会显示错名字。`@functools.wraps(fn)` 把原函数的这些属性复制过来。

示例断言 `inc.__name__ == "inc"`，文档字符串里仍有“加一”。写装饰器时默认加上 `wraps`，除非你故意要一个全新的函数对象并且不关心元数据。

`wraps` 还会更新 `__wrapped__`，指向被包住的函数。调试时可以沿这条链找到原函数。它不会自动让签名检查变魔术，类型检查器对装饰器仍然比较严格。

## 带参数的装饰器

`tag("outer")` 不是装饰器，它是 **制造装饰器的函数**。调用之后才得到真正的装饰器，那个装饰器再接收函数。所以结构是三层：参数、被装饰的函数、实际的包装。

少一层是最常见的笔误：写成了 `def tag(fn)` 却用 `@tag("outer")` 去调用。层数要和 `@` 后面的调用次数一致。

## 叠加顺序

```python
@tag("outer")
@tag("inner")
def value() -> int:
    return 1
```

等价于 `value = tag("outer")(tag("inner")(value))`。离函数最近的装饰器先包。调用时最外层先进入。示例的结果是 `("outer", ("inner", 1))`。

读这种代码时从下往上看“谁先包住原函数”，从上往下看“调用时谁先执行”。两个方向不要混成一句口诀。

## 类也可以当装饰器

实现了 `__call__` 的类，实例可以当装饰器返回的包装物。需要保存多份状态时，类比往函数上挂属性清楚。本教程的示例用函数，是因为状态只有一个计数。不要为了“更面向对象”把三行闭包扩成一个类。

## 机制

装饰器是接受可调用对象、返回可调用对象的可调用对象。`@deco` 写在 `def` 上面，等价于 `fn = deco(fn)`。这发生在函数定义时，不是调用时。

包装函数如果不抄元数据，`__name__` 和 `__doc__` 会变成包装器的。`functools.wraps(fn)` 把这些抄过来，也把 `__wrapped__` 留下，调试和测试可以拿到原函数。

带参数的装饰器是三层：最外层接收装饰器参数，中间接收函数，最内层接收原函数的参数。少一层就会把函数当成配置，或者把参数当成函数。

多个装饰器从下往上应用。写出来的顺序是：

```text
@a
@b
def f(): ...
```

等价于 `f = a(b(f))`。调用时先进入 `a` 的包装，再进入 `b` 的包装，再进原函数。读代码时从靠近 `def` 的那个开始套。

类如果实现 `__call__`，实例也可以当装饰器。它适合包装器需要保存配置的情况。不要为了这个去写元类。

装饰器会多一层调用。放在每秒百万次的最内层之前先测量。更多的问题是它改变了签名和异常，让调用方看不见真实函数。

## 会出事的写法

- 包装器忘记返回原函数的返回值。所有调用变成 `None`。
- 用装饰器做权限检查，失败时返回 `False` 而不是抛异常。调用方继续往下走。
- 装饰器里用可变默认参数或全局字典按函数名做缓存，却没有上限。`functools.cache` 和 `lru_cache` 要知道键必须可哈希，并且缓存会持有参数和返回值。
- `@staticmethod`、`@classmethod` 和自定义装饰器的顺序叠错。离 `def` 近的先应用。

## 示例对照

`examples/part_b/b04_decorators.py` 应断言包装后的行为、`__name__` 仍是原函数（用了 `wraps` 时），以及两层装饰器的执行顺序。如果打印顺序是外层进、内层进、函数、内层出、外层出，那就是 `a(b(f))`。

## 加练

1. 写一个装饰器 `once`，第一次调用执行原函数，之后返回第一次的结果。说出它不能装饰哪类函数。
2. 为什么 `once` 的缓存要挂在包装器上，而不是挂在默认参数上？

参考答案：

1. 无参或参数不影响结果的函数才安全。有参数时必须把参数纳入键，否则不同参数会共用第一次的结果。返回可变对象时，调用方改结果会污染缓存。
2. 默认参数能做，但读起来像事故。属性挂在包装函数上，每个被装饰函数有自己的包装器，缓存不会串到别的函数。

## 面试

### Q1. `@deco` 在什么时候执行？

**考点**：定义期和调用期。

**回答**：

1. `deco(fn)` 在定义函数时执行，返回值替换原名字。
2. 包装器的函数体在每次调用时执行。
3. 所以装饰器参数里的错误会在导入时暴露，包装器里的错误在调用时暴露。

### Q2. 为什么需要 `wraps`？

**考点**：元数据和调试。

**回答**：

1. 不抄的话，`__name__`、`__qualname__`、`__doc__` 都变成包装器的，日志和帮助信息指向错误的函数。
2. `wraps` 还设置 `__wrapped__`，可以剥开一层。
3. 它不保留完整签名的运行时强制。类型检查器需要 `ParamSpec` 才能把参数类型传进去。3.12 可以写，但运行时仍不校验。

### Q3. 两个装饰器谁先执行？

**考点**：应用顺序和调用顺序相反。

**回答**：

1. 靠近函数的装饰器先应用，也就是先包装原函数。
2. 调用时最外层先进入。
3. 记法：`@a` 在 `@b` 上面，就是 `a(b(f))`。不要背“从上到下调用”而不说明是应用还是调用。

## 常见错误

- 包装函数忘记 `return fn(*args, **kwargs)`，被装饰的函数变成总是返回 `None`。
- 忘记 `wraps`，测试框架按名字找测试时找不到。
- 装饰器在导入时执行。不要在装饰器里连接网络。注册到一个列表里是可以的，那是定义期想要的副作用。

## 练习

1. 写一个装饰器 `double_result`，把原函数的返回值乘 2。假设返回值是数字。
2. 两个这样的装饰器叠在一起，`lambda: 3` 的结果是多少？先预测再跑。
3. `wraps` 复制了什么，没有自动做什么？

参考答案：

1. 包装函数 `return fn(*args, **kwargs) * 2`，并用 `wraps`。
2. 先包的那一层先乘，后包的再乘，结果是 `12`。两层都是乘 2。
3. 它复制名字、文档、注解等元数据，并设置 `__wrapped__`。它不会把类型注解变成运行时校验。

## 小结

`@decorator` 就是调用装饰器再把名字绑到返回值上。用 `wraps` 保留原函数的身份。带参数就多一层工厂函数。离 `def` 最近的装饰器最先包住原函数。
