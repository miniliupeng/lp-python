# B13　小项目：库存流水

> 示例：`examples/part_b/b13_inventory.py`

## 学完你能做什么

把 dataclass、枚举和“拒绝不可能的状态”放进一个能讲清楚的小模型。这是 B 阶段的综合练习，不引入新语法。

## 规则

- 一条流水有货号、数量、方向。数量必须是正数。方向只有入库和出库，用 `Side` 枚举，不使用字符串 `"in"` 散落在条件里。
- 库存按货号累加。出库之后不能变成负数。拒绝时原来的数量保持不变。
- 非法流水在构造时就失败，不会进入库存。

这些规则写在 `Movement.__post_init__` 和 `Stock.apply` 里。`__post_init__` 在生成的 `__init__` 之后运行，适合检查字段之间的关系。数量这个字段自己的范围也放在这里，调用方就不可能拿到一个 `qty == 0` 的 `Movement`。

`frozen=True` 让流水一旦创建就不能改数量。库存对象是可变的，因为 `on_hand` 会更新。两种可变性放在不同的类型上，读代码时能看出来谁是记录、谁是账。

## 失败时不要改一半

`apply` 先算出 `nxt`，确认不小于 0，再写回字典。如果先减再发现不够、然后再加回去，中间任何异常都会让账停在半更新的状态。先算后写，是这个小例子能做的全部事务。真的数据库事务在 D06。

拒绝用 `ValueError`。调用方如果要区分“数量不合法”和“库存不足”，应该换成两种自定义异常。示例故意只用一种，是为了把控制流留短。你在练习里可以拆开。

枚举用 `is` 比较：`move.side is Side.IN`。成员是单例，这比和字符串比较更不容易出现 `"In"` 这种大小写错误。

## 断言就是规格

- 入库 5、出库 2，剩余 3。
- 再出库 4，抛异常，剩余仍然是 3。
- 数量 0 的流水构造不出来。

你改规则时，先改断言还是先改实现都可以，但两边最后要一致，并且失败信息要能指出是哪一条规格破了。

## 这个模型故意没有的东西

没有并发。两个线程同时 `apply` 会互相覆盖字典，B 阶段不解决这个。D07 讨论共享状态要放进队列，由单独的工作者顺序应用。

没有持久化。进程结束，字典就没了。D06 用 SQLite 把“先算后写”变成真正的提交和回滚。

没有货号是否存在于商品主数据的检查。那是另一个边界。`Stock` 只负责数量不变量。把所有规则塞进一个类，类会变成无法测试的脚本。

## 机制

库存流水是一个小领域模型，用来把类、枚举和测试放在一起。不变量要先写出来：

1. 数量是正整数。0 和负数不是一笔合法流水。
2. 出库不能让库存变成负数。失败时库存完全不变，不能先减再发现不够。
3. 每一笔成功的变动都留下记录，记录不可变。
4. 入库和出库是枚举，不是随意字符串。

失败时不要改一半，意味着检查和修改之间不能插入一次“已经 append 但数量没改”的状态。先算结果，合法再同时更新余额和流水。单线程里这是顺序问题。多线程里还需要锁或把模型限制在一个主人线程里，D07 再讲。

测试就是规格。先写“出库超过库存时余额不变”，再写实现。断言看余额和流水长度，不看私有字典的键名。

这个模型故意没有的东西：持久化、并发、权限、跨仓库调拨。加上它们之前，单进程的不变量应该已经测试通过。否则数据库只会把错误状态保存得更久。

## 会出事的写法

- 先 `stock -= n` 再判断小于 0 然后加回去。中途异常会留下半笔。
- 用字符串 `"in"` / `"out"` 且大小写不一致。用枚举。
- 流水列表和余额分开更新，中间调用了外部函数。外部函数再进来读，会看到不一致。
- 测试只测成功路径。超卖才是这个模型的存在理由。

## 示例对照

`examples/part_b/b13_inventory.py` 断言入库增加余额、出库减少余额、超额出库抛异常且余额与流水长度都不变。读测试的名字就能说出不变量。实现若能绕过方法直接改属性，那是 Python 的开放对象模型，不是测试失败。契约靠接口和测试，不靠语言把属性锁死。需要锁死再用冻结数据类或 `property`。

## 加练

1. 连续两次相同的出库请求，模型会减两次。怎样表示“这是同一次请求的重放”？
2. 为什么记录用元组或冻结数据类，而不是字典？

参考答案：

1. 给请求一个调用方生成的幂等键，存在集合里。见过的键直接返回上一次的结果，不再改余额。键的集合要和余额一起更新。
2. 记录不该被事后改数量。字典默认可变，放进列表后仍能改。冻结对象或元组把“历史不可改”写进类型。

## 面试

### Q1. 怎样保证失败时库存不变？

**考点**：临时状态。

**回答**：

1. 在修改任何属性之前完成全部检查。
2. 更新时先算新余额，再一次性写入余额和流水。
3. 不要先改再回滚，除非回滚本身在 `try` 里并且测试覆盖了回滚路径。单进程优先不产生需要回滚的中间状态。

### Q2. 这个模型和数据库事务是什么关系？

**考点**：不变量要从内存模型延续到持久化。

**回答**：

1. 内存里的“要么全改要么不改”就是事务想保存的性质。
2. 数据库用事务把余额更新和插入流水放在同一个提交里。D06 的 sqlite 示例演示回滚。
3. 只在 Python 里检查、提交时却是两条独立语句，进程在中间崩溃仍会半更新。

### Q3. 为什么不在这个练习里直接上 ORM？

**考点**：问题边界。

**回答**：

1. 超卖是领域规则，不是 ORM 的功能。
2. 先用测试把规则固定，再选择存储。
3. ORM 负责映射和事务边界。它不会知道“出库不能为负”，除非你把这条写进模型和约束。数据库也可以加 `CHECK (qty >= 0)` 当最后一道门。

## 练习

1. 增加 `Side` 不能表达的第三种操作之前，先说出现有模型为什么不需要“调整到绝对数量”。如果需求就是盘点到一个绝对值，应该新增类型，而不是把负数塞进出库。
2. 让库存不足抛出你自己的 `InsufficientStock`，数量不合法仍抛 `ValueError`。补断言。
3. 为什么 `Movement` 冻结了，`Stock` 却没有？

参考答案：

1. 入库和出库都是正数加方向，不变量好检查。绝对盘点是另一种命令：目标数量本身可以是 0。用新的类型表达，不要用 `OUT` 加负数。
2. `class InsufficientStock(Exception): ...`，在 `nxt < 0` 时抛它。构造非法数量的测试仍然期待 `ValueError`。
3. 流水是已经发生的事实，改数量会伪造历史。账本是当前状态，应用流水就是在更新它。

## 小结

用枚举限定方向，用冻结的数据类保存不可改的流水，用一个方法维护“库存不为负”。失败发生在写回之前。这个模型是后面持久化和并发章节的起点，而不是一个缩小版的进销存系统。
