# B13　小项目：库存流水

> 示例：`examples/part_b/b13_inventory.py`

## 学完你能做什么

把 dataclass、枚举和“拒绝不可能的状态”放进一个能讲清楚的小模型。这是 B 阶段的综合练习，不引入新语法。

## 规则

- 一条流水有货号、数量、方向。数量必须是正数。方向只有入库和出库，用 `Side` 枚举，不使用字符串 `"in"` 散落在条件里。
- 库存按货号累加。出库之后不能变成负数。拒绝时原来的数量保持不变。
- 非法流水在构造时就失败，不会进入库存。

这些规则写在 `Movement.__post_init__` 和 `Stock.apply` 里。`__post_init__` 在生成的 `__init__` 之后运行，适合检查字段之间的关系。数量这个字段自己的范围也放在这里，调用方就不可能拿到一个 `qty == 0` 的 `Movement`。

`frozen=True` 让流水一旦创建就不能改数量。库存对象是可变的，因为 `on_hand` 会更新。两种可变性放在不同的类型上，读代码时能看出来谁是记录、谁是账。

## 失败时不要改一半

`apply` 先算出 `nxt`，确认不小于 0，再写回字典。如果先减再发现不够、然后再加回去，中间任何异常都会让账停在半更新的状态。先算后写，是这个小例子能做的全部事务。真的数据库事务在 D06。

拒绝用 `ValueError`。调用方如果要区分“数量不合法”和“库存不足”，应该换成两种自定义异常。示例故意只用一种，是为了把控制流留短。你在练习里可以拆开。

枚举用 `is` 比较：`move.side is Side.IN`。成员是单例，这比和字符串比较更不容易出现 `"In"` 这种大小写错误。

## 断言就是规格

- 入库 5、出库 2，剩余 3。
- 再出库 4，抛异常，剩余仍然是 3。
- 数量 0 的流水构造不出来。

你改规则时，先改断言还是先改实现都可以，但两边最后要一致，并且失败信息要能指出是哪一条规格破了。

## 这个模型故意没有的东西

没有并发。两个线程同时 `apply` 会互相覆盖字典，B 阶段不解决这个。D07 讨论共享状态要放进队列，由单独的工作者顺序应用。

没有持久化。进程结束，字典就没了。D06 用 SQLite 把“先算后写”变成真正的提交和回滚。

没有货号是否存在于商品主数据的检查。那是另一个边界。`Stock` 只负责数量不变量。把所有规则塞进一个类，类会变成无法测试的脚本。

## 练习

1. 增加 `Side` 不能表达的第三种操作之前，先说出现有模型为什么不需要“调整到绝对数量”。如果需求就是盘点到一个绝对值，应该新增类型，而不是把负数塞进出库。
2. 让库存不足抛出你自己的 `InsufficientStock`，数量不合法仍抛 `ValueError`。补断言。
3. 为什么 `Movement` 冻结了，`Stock` 却没有？

参考答案：

1. 入库和出库都是正数加方向，不变量好检查。绝对盘点是另一种命令：目标数量本身可以是 0。用新的类型表达，不要用 `OUT` 加负数。
2. `class InsufficientStock(Exception): ...`，在 `nxt < 0` 时抛它。构造非法数量的测试仍然期待 `ValueError`。
3. 流水是已经发生的事实，改数量会伪造历史。账本是当前状态，应用流水就是在更新它。

## 小结

用枚举限定方向，用冻结的数据类保存不可改的流水，用一个方法维护“库存不为负”。失败发生在写回之前。这个模型是后面持久化和并发章节的起点，而不是一个缩小版的进销存系统。
