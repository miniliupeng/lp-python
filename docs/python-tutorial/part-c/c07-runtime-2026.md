# C07　自由线程、子解释器与 3.13–3.15

> 示例：`examples/part_c/c07_version_probe.py`。这一章的新语法 **不** 放进可执行示例。示例只在当前解释器上探测模块在不在。本环境是 CPython 3.12.3，探测结果是 3.13 及以上的模块尚不存在。

## 学完你能做什么

把 2026 年 11 月的运行时地图说准确：什么已经是语言的一部分，什么仍是可选构建，什么不要写成“GIL 已经没了”。

## 版本时间

| 版本 | 发布 | 和这一章有关的点 |
| --- | --- | --- |
| 3.12 | 2023-10 | 每解释器一把 GIL（PEP 684）成为稳定基础。本教程示例跑在这一档。 |
| 3.13 | 2024-10 | 自由线程构建实验出现（PEP 703）。实验性 JIT（PEP 744）默认不在普通构建里。`locals()` 语义写进 PEP 667。 |
| 3.14 | 2025-10-07 | 自由线程成为官方支持的 **可选** 构建（PEP 779，第二阶段）。`concurrent.interpreters`、t-string、延迟注解、`annotationlib`。 |
| 3.15 | 2026-10-09 | `lazy` 导入、内置 `frozendict` 和 `sentinel`、推导式解包、默认 UTF-8。JIT 仍是实验特性，但有明显升级。写作时文档站可见 3.15.2。 |

官方文档是这些句子的依据。博客里的“Python 3.13 移除了 GIL”是错的。

## 自由线程不是默认解释器

PEP 703 把 GIL 变成可以在编译期关掉的东西。3.13 的自由线程构建明确实验。3.14 完成了实现上的主要工作，单线程性能损失大约在 5% 到 10% 这个量级（随平台和编译器变化，官方 what’s new 的说法），并成为受支持的可选构建。PEP 779 写明：第三阶段——把自由线程变成默认——要另写 PEP。到 3.15 的 what’s new，默认解释器仍然不是“已经去掉 GIL 的那一个”。

3.15 的发布说明里有一句容易看错：官方 macOS 安装包默认带上自由线程支持。这是安装包里提供这个构建，不是所有平台上的 `python` 命令都关掉了 GIL。3.13 及以上用 `sys._is_gil_enabled()` 看 **当前进程**。3.12 没有这个函数，示例在 3.13 之前只断言属性不存在。

自由线程下，多条线程可以同时执行 Python 字节码。你的数据竞争会从“偶尔”变成“很容易复现”。原来靠 GIL 碰巧没拆开的 `+=` 更不能裸奔。C 扩展也要声明自己支持这种构建。性能上，3.14 的专门化解释器已经能在自由线程模式里工作；官方同时写明，3.14 的自由线程构建不支持当时的 JIT。

## JIT 仍要打开

3.13 的 JIT 是拷贝-补丁（copy-and-patch）的实验编译器，普通配置不包含它。3.14 的官方 macOS 和 Windows 二进制带了实验 JIT，用环境变量 `PYTHON_JIT=1` 打开，默认仍是关的。文档给出的早期影响大约从变慢一成到变快两成，随负载变化，并且原生调试器还不能很好地展开 JIT 帧。3.15 的 what’s new 报告：在开启优化的 x86-64 Linux 上，相对普通解释器大约 7% 到 8% 的几何平均提升；在 AArch64 macOS 上相对尾调用解释器大约 11% 到 12%。这是基准套件的结果，不是你的服务会自动变快的承诺。

不要在简历或设计文档里写“我们用的 Python 3.15 自带生产级 JIT”。它到 3.15 仍被称为实验特性。测量一个具体负载，再决定打不打开。

## 子解释器

3.12 起，子解释器各自持有一把 GIL，可以在不同核上同时执行 Python。3.14 才把这件事放进标准库 `concurrent.interpreters`（PEP 734）。在此之前只有 C API。

子解释器默认不共享对象。这比线程更接近“同一进程里的多个隔离世界”，也比进程少一次操作系统进程的开销。限制也很具体，3.14 文档列了：启动还没优化、每个解释器的内存还有浪费、能共享的对象种类很少、不少第三方扩展还没准备好。它不是线程的无脑替换。CPU 密集、任务边界清楚、依赖库支持时，值得做实验。示例在 3.14 之前断言这个模块不存在，避免在 3.12 上写出无法运行的导入。

## 3.14 的语言变化

- **t-string（PEP 750）。** `t"Hello {name}"` 的结果是 `string.templatelib.Template`，保留静态片段和插值。它不自动做 HTML 转义。安全来自你怎么处理这个模板，不是来自字母 `t`。
- **延迟注解（PEP 649 / 749）。** 见 B09。读取用 `annotationlib`。
- **`except` 可以不写括号（PEP 758）。** `except TimeoutError, ConnectionRefusedError:` 在 3.14 合法。3.12 必须写成元组。教程示例保持 3.12 的括号写法，两种版本都能读。
- **离开 `finally` 的 `return` / `break` / `continue`（PEP 765）。** 编译器给出 `SyntaxWarning`。3.12 仍是悄悄改变控制流，A10 的示例保留了那种旧行为，用来提醒你不要写。

## 3.15 的语言变化

- **`lazy` 导入（PEP 810）。** `lazy import json` 在模块顶层合法，真正使用名字时才加载。放进函数、类体或 `try` 里是 `SyntaxError`。失败也推迟到第一次使用。还有模块级 `__lazy_modules__`，以及 `-X lazy_imports`。这不是 3.12 的语法，示例不写。
- **`frozendict`（PEP 814）。** 内置不可变映射， **不是** `dict` 的子类。内容和键都可哈希时，它自己也可哈希。相等性不看插入顺序，但会保留插入顺序。`isinstance(obj, dict)` 不会把 `frozendict` 认出来。需要同时接受时，检查 `dict` 与 `frozendict`，或检查 `collections.abc.Mapping`。
- **`sentinel`（PEP 661）。** 用来做可打印、可序列化的哨兵，替代随手 `object()`。3.12 继续用 `object()`。
- **推导式里的 `*` / `**`（PEP 798）。** 3.12 的推导式没有这个语法。
- **默认编码 UTF-8（PEP 686）。** `open` 不写 `encoding` 时用 UTF-8。`PYTHONUTF8=0` 或 `-X utf8=0` 可以退回旧行为。教程从 A04 起就要求写明 `encoding="utf-8"`，所以这条默认值变化不会改变示例。
- **`profiling` 包（PEP 799）。** `profiling.tracing` 是原来的 `cProfile`，`cProfile` 仍留作别名。`profile` 模块计划在 3.17 移除。采样分析器 Tachyon 在 `profiling.sampling`，可以按 PID 附着到正在运行的进程。3.12 做确定性分析时仍然用 `cProfile`，C09 就是这样。

## 常见错误

- 把“可选构建已经官方支持”说成“默认没有 GIL”。
- 在 3.12 的代码里写 `t""` 或 `lazy import`，却没标明那是更高版本的语法。
- 用 `isinstance(obj, dict)` 打算接收 3.15 的 `frozendict`。它不是子类。

## 练习

1. 在 3.12 上运行版本探测示例，哪两个模块应当不存在？
2. 怎样判断一个 3.14 进程当前有没有 GIL？
3. `frozendict` 能通过 `isinstance(x, dict)` 吗？

参考答案：

1. `annotationlib` 和 `concurrent.interpreters`。`profiling` 也要到 3.15。
2. `sys._is_gil_enabled()`。不要看版本号猜。
3. 不能。它直接继承 `object`。需要映射的行为时用 `collections.abc.Mapping`。

## 小结

2026 年的默认 CPython 仍是带 GIL 的构建。自由线程是受支持的可选项，JIT 仍是实验。3.14 带来子解释器标准库、t-string 和延迟注解。3.15 带来惰性导入、`frozendict` 和默认 UTF-8。教程的可执行示例停在 3.12 语法上，避免一份源码两种意思。
